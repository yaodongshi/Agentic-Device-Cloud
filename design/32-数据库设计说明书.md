## 1. 设计概述

### 1.1 存储选型结论与职责边界

ADC 的数据资产按"权威性与访问热度"划分为两类存储：PostgreSQL 16+ 承载全部权威数据（状态、台账、审计、工单、计量），Valkey 8+ 只承载易失的运行时热数据。选型理由：PG 的事务、约束与分区能力是审计不可抵赖（SEC-07）与工单状态机（ADR-05）的前提；Valkey 负责心跳、在线状态、限流计数器与 HITL 唤醒通道（ADR-05 保留项），这些数据允许丢失且必须低时延。职责边界如下：

| 数据类别 | 存储位置 | 理由 | 允许丢失 |
|---|---|---|---|
| 租户/用户/角色/配额台账 | PostgreSQL | 商业化的权威账本，需要事务与约束 | 否 |
| 设备注册信息与凭证哈希 | PostgreSQL | 凭证是纳管根基（FR-010），吊销必须持久 | 否 |
| 工具定义与风险等级 | PostgreSQL | 风险判定依据（FR-006），须可审计 | 否 |
| HITL 审批工单与状态机 | PostgreSQL | ADR-05：合规与追责核心数据，不可抵赖 | 否 |
| 审计日志 | PostgreSQL（分区表） | SEC-07：append-only，等保审计要求 | 否 |
| 计量埋点事件 | PostgreSQL | FR-016：账单对账依据，幂等去重 | 否（最终一致允许 5 分钟延迟） |
| 设备在线状态、心跳时间 | Valkey | 高频写、短 TTL，PG 定期批量落盘 last_heartbeat_at | 是 |
| 限流 token bucket 计数 | Valkey | SEC-12：高频原子扣减 | 是 |
| HITL 跨节点唤醒消息 | Valkey（后续 NATS JetStream，ADR-02） | 通知通道，非状态存储 | 是 |
| 会话级工具聚合缓存 | Valkey | 加速 tools/list（NFR-003：P95 200ms） | 是 |
| LLM Token 热计量缓冲 | Valkey + 异步落 PG | 高频累加先入缓存，定期聚合写入 adc_usage_events | 短暂允许 |

底线原则：Valkey 中的数据在 PG 中必须有可重建路径；PG 中的数据不依赖 Valkey 存活。

### 1.2 访问模式盘点

数据建模以访问模式为第一输入。按 FR 验收标准与 NFR 指标梳理核心读写场景：

| 场景 | 类型 | 频次 | 单次数据量 | 时延要求 | 设计响应 |
|---|---|---|---|---|---|
| 设备心跳（在线状态） | 写 | 每设备 10~30 秒 | 1 行 | 无感 | 只写 Valkey TTL，PG 批量落盘 last_heartbeat_at，不对 PG 高频写 |
| tools/list 工具聚合 | 读 | 每 Agent 会话建立与刷新 | 每租户数百行 | P95 200ms（NFR-003） | tenant 冗余键 + 组合索引 + Valkey 会话缓存 |
| 工具定义同步（设备上报） | 写 | 设备上线/变更 | 每设备 1~数十行 | 30 秒内可见 | upsert on conflict，schema_version 递增 |
| 工具调用（免审） | 读+写 | 高峰每租户每秒数十次 | 1 次调用 1 条审计 | 主链路 P95 500ms | 审计写入异步化（ADR-06），不在调用事务内 |
| HITL 工单创建/决策 | 写 | 高危指令触发，低频高价值 | 1~2 行 | 卡片 30 秒内送达 | 工单 PG 主存，Valkey 仅唤醒 |
| 工单超时扫描 | 读写 | 每分钟 1 次 | 每次数十行 | 分钟级 | 部分索引只扫 PENDING |
| 审计多条件查询 | 读 | 控制台按需 | 每次数十行分页 | 3 秒内返回（FR-013） | 时间分区裁剪 + 租户前缀索引 |
| 审计导出 | 读 | 低频 | 单次上限 10 万条 | 异步任务 | 分区顺序扫描 |
| 计量埋点写入 | 写 | 与调用量同频 | 每次 1~2 行 | 允许 5 分钟延迟 | 批量 INSERT + 幂等键 |
| 月度账单聚合 | 读 | 每月每租户 1 次 | 聚合扫描 | 无实时要求 | V1.5 物化视图或后台任务 |
| 配额扣减 | 读改写 | 与注册/调用同频 | 1 行 | 同步即时 | 条件原子 UPDATE，热计数走 Valkey |

数据规模基线（假设值，需压测校准）：V1.0 目标 1 万在线设备/单节点、10 万级设备集群；按 1 万设备、每设备 5 工具、每日每设备 100 次调用估算，审计日志日均 100 万行、单月约 3000 万行、180 天留存约 1.8 亿行——按月分区后单分区 3000 万行以内，索引与清理成本可控；计量事件量与审计同数量级；工单仅风险 2 及以上触发，日均约千级。

### 1.3 命名规范

- 表名：统一 `adc_` 前缀 + snake_case 复数名词（如 `adc_approval_tickets`）。
- 字段名：snake_case，布尔字段用 `is_`/`has_` 前缀，时间字段以 `_at` 结尾，外键以 `_id` 结尾。
- 主键：一律 `id UUID`，默认值 `gen_random_uuid()`（PG 13+ 内置，不依赖 pgcrypto）。
- 状态字段：VARCHAR(16) + CHECK 约束枚举（字符串枚举便于日志与外部协议直读，比 PG enum 类型迁移友好；约束可防止脏数据）。
- 保留字规避：不使用 `order`、`group`、`user` 等保留字；`user` 类表命名为 `adc_users` 规避。

### 1.4 通用约束规范

- 主键：UUID 客户端或数据库生成均可，禁止自增整型作为对外标识（防遍历、合并部署安全）。
- 时间戳：全部 `TIMESTAMPTZ`（UTC 存储）；会话与展示统一 `Asia/Shanghai`（FR-014 异常场景要求），由应用层 `SET timezone` 或连接参数控制，不在库里写死。
- 软删除：台账类表（租户、用户、设备、分组、工具、API Key）用 `deleted_at TIMESTAMPTZ`，查询层统一过滤；审计、计量、工单、通知为不可删数据，不用软删除。
- 软删除与唯一约束冲突：唯一性用 `WHERE deleted_at IS NULL` 的部分唯一索引实现（见 3.x 各表），设备码例外（全局唯一、永不复用，FR-011 重复码整行回滚）。
- 版本列：工单等状态机表带 `version INTEGER DEFAULT 1`，作为乐观锁兜底。
- 冗余租户键：高频按租户查询的子表冗余 `tenant_id`，写入时应用层强制与父表一致性校验（见 4.1）。
- 表注释：每张表与关键字段带 `COMMENT ON`，作为数据字典基线。
- 字符集：UTF-8；数据库 collation 用 `C` 或 `en_US.UTF-8` 均可，禁止 `zh_CN.GBK`。

### 2.3 实体关系说明

- 租户为一切数据的隔离根：除平台级角色外，全部业务表经 tenant_id 直接或间接挂到租户，删除租户时逐级处理（见 6.5）。
- 设备分组是租户内树形结构（parent_id 自引用），设备通过 group_id 挂组，删组时设备自动脱组（ON DELETE SET NULL），不误删设备。
- 设备与工具为一对多强聚合，工具生命周期完全随设备（ON DELETE CASCADE）；工具行冗余 tenant_id 以服务高频租户聚合。
- 工单是"调用请求"的持久快照：device_id/tool_id 关联实体（tool_id 可空，兼容工具已删除的存量工单），tool_name 快照保证历史语义完整；工单经 api_key_id 与 Agent 调用链打通（FR-009 审计要求）。
- 审计日志、计量事件与业务表之间是弱引用（无外键），避免写放大与分区表外键限制，关联靠 request_id/api_key_id 等业务键对账。
- 通知从属于工单（ticket_id），但非级联删除——工单永久留存，通知记录随其留存作为推送留痕。

| 枚举 | 取值 | 说明 |

| 租户状态 | ACTIVE / SUSPENDED / DELETING / DELETED | DELETING 为 7 天冷静期（FR-008） |
| 设备状态 | ONLINE / OFFLINE / ERROR / FROZEN / RETIRED | FROZEN 为冻结态，RETIRED 为注销态（FR-010） |
| 设备类 | A / B | A 原生 MCP Server，B Legacy Bridge（ADR-15） |

## 3. 完整 DDL

> 以下 SQL 面向 PostgreSQL 16，顺序执行即可建出全库。多租户隔离策略见 3.0 节说明。

### 3.0 多租户隔离策略（先于建表说明）

推荐方案：**tenant_id 列 + 应用层强制校验为主，行级安全（RLS）作为 V1.5 私有化场景的可选兜底**。理由：

1. ADC 的访问者包括设备连接、Agent MCP 调用、审批回调、后台任务等非交互连接，RLS 要求每个连接先 `SET app.tenant_id`，在连接池与异步任务场景下极易串号，风险高于收益。
2. 网关数据面路径是超高频路径，应用层校验（鉴权中间件注入 tenant 上下文，仓储层强制 WHERE tenant_id）已经覆盖 99% 的访问；RLS 主要防的是"拿到裸库账号"的攻击者，该场景用最小权限账号（应用账号仅 CRUD 无 DDL）同样能压制。
3. RLS 与分区表、物化视图、异步逻辑复制存在交互复杂性，V1.0 单实例阶段不引入。
4. 兜底机制：为审计场景预留 `adc_readonly` 角色，仅授权 SELECT；应用代码统一走仓储层，禁止裸 SQL 绕过。

### 3.1 adc_tenants（租户+配额）

```sql
CREATE TABLE adc_tenants (
    id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    code                 VARCHAR(64)  NOT NULL,             -- 租户编码，全局唯一
    name                 VARCHAR(255) NOT NULL,
    status               VARCHAR(16)  NOT NULL DEFAULT 'ACTIVE'
                         CHECK (status IN ('ACTIVE','SUSPENDED','DELETING','DELETED')),
    quota_devices        INTEGER NOT NULL DEFAULT 100,      -- 设备数配额（NFR-002 单租户上限 1 万）
    quota_calls_monthly  BIGINT  NOT NULL DEFAULT 100000,   -- 月调用量配额
    quota_concurrent     INTEGER NOT NULL DEFAULT 10,       -- 并发连接配额
    used_devices         INTEGER NOT NULL DEFAULT 0,        -- 已用设备数（冗余计数，见 6.2）
    used_calls_month     BIGINT  NOT NULL DEFAULT 0,        -- 当月已用调用量（冗余计数）
    billing_period_start DATE,                              -- 计费周期起点（V1.5 计费用）
    timezone             VARCHAR(64) NOT NULL DEFAULT 'Asia/Shanghai',
    locale               VARCHAR(16) NOT NULL DEFAULT 'zh-CN',
    metadata             JSONB NOT NULL DEFAULT '{}',
    created_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at           TIMESTAMPTZ,
    CHECK (used_devices <= quota_devices),
    CHECK (used_calls_month <= quota_calls_monthly)
);
CREATE UNIQUE INDEX uq_tenants_code ON adc_tenants (code) WHERE deleted_at IS NULL;
CREATE INDEX idx_tenants_status ON adc_tenants (status) WHERE deleted_at IS NULL;
COMMENT ON TABLE adc_tenants IS '租户与配额台账（FR-008）。配额在线校验走 Valkey 计数，本表为权威账本与对账基准';
COMMENT ON COLUMN adc_tenants.status IS 'ACTIVE 正常 / SUSPENDED 停用（踢下线、工单失效）/ DELETING 冷静期 / DELETED 已删除';
```

### 3.2 adc_users（用户）

```sql
CREATE TABLE adc_users (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id     UUID NOT NULL REFERENCES adc_tenants(id),
    username      VARCHAR(128) NOT NULL,
    display_name  VARCHAR(255),
    email         VARCHAR(255),
    phone         VARCHAR(32),
    password_hash TEXT,                                      -- Argon2id；SSO 用户为空
    auth_source   VARCHAR(16) NOT NULL DEFAULT 'LOCAL'
                  CHECK (auth_source IN ('LOCAL','OIDC')),
    status        VARCHAR(16) NOT NULL DEFAULT 'ACTIVE'
                  CHECK (status IN ('ACTIVE','DISABLED','LOCKED')),
    last_login_at TIMESTAMPTZ,
    metadata      JSONB NOT NULL DEFAULT '{}',
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at    TIMESTAMPTZ
);
CREATE UNIQUE INDEX uq_users_tenant_username ON adc_users (tenant_id, username) WHERE deleted_at IS NULL;
CREATE INDEX idx_users_tenant ON adc_users (tenant_id) WHERE deleted_at IS NULL;
COMMENT ON TABLE adc_users IS '租户内用户（FR-008 组织成员：平台管理员/租户管理员/审批人/只读审计员/Agent 开发者）';
```

### 3.3 adc_roles 与 adc_user_roles（RBAC）

```sql
CREATE TABLE adc_roles (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id   UUID REFERENCES adc_tenants(id),             -- 空表示平台级角色
    role_code   VARCHAR(64) NOT NULL,
    scope       VARCHAR(16) NOT NULL CHECK (scope IN ('PLATFORM','TENANT')),
    description TEXT,
    permissions JSONB NOT NULL DEFAULT '[]',                 -- 权限点数组，如 ["device:read","ticket:approve"]
    is_system   BOOLEAN NOT NULL DEFAULT FALSE,              -- 系统预置角色不可删
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uq_roles_scope_code ON adc_roles (scope, COALESCE(tenant_id, '00000000-0000-0000-0000-000000000000'), role_code);
CREATE INDEX idx_roles_tenant ON adc_roles (tenant_id);

CREATE TABLE adc_user_roles (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID NOT NULL REFERENCES adc_users(id) ON DELETE CASCADE,
    role_id     UUID NOT NULL REFERENCES adc_roles(id) ON DELETE CASCADE,
    tenant_id   UUID NOT NULL REFERENCES adc_tenants(id),    -- 冗余：约束"用户与角色同租户"
    granted_by  UUID REFERENCES adc_users(id),
    granted_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at  TIMESTAMPTZ,
    UNIQUE (user_id, role_id)
);
CREATE INDEX idx_user_roles_tenant ON adc_user_roles (tenant_id);
COMMENT ON TABLE adc_roles IS '角色定义（FR-014 菜单级 RBAC）。平台级：PLATFORM_ADMIN；租户级：TENANT_ADMIN/APPROVER/AUDITOR/DEVELOPER';
```

## 4. 索引与性能设计

索引按"每个索引必须能指出服务的具体查询"原则设计，以下为关键查询路径与对应索引：

| 查询路径 | 频次 | 索引 | 理由 |
|---|---|---|---|
| 设备按租户列表/状态筛选（控制台） | 高 | `idx_devices_tenant_status (tenant_id, status)` | 等值 tenant + 等值 status，复合索引左前缀匹配 |
| 设备按分组查询（FR-011 组内聚合/下发） | 高 | `idx_devices_tenant_group (tenant_id, group_id)` | 组查询总是带租户（隔离校验），租户放最左列 |
| 工具聚合 tools/list（FR-003，NFR-003 P95 200ms） | 极高 | `idx_tools_tenant_risk (tenant_id, risk_level) WHERE is_enabled`；热点走 Valkey 会话缓存 | 租户级全量工具聚合；risk_level 列服务拦截判定与风险筛选 |
| 工具按设备查询 | 高 | `UNIQUE (device_id, tool_name)` 约束自带索引 | 唯一约束本身即索引，upsert 同步路径 |
| 审计多条件筛选（FR-013 时间+租户+设备+状态） | 高 | `idx_audit_tenant_time / idx_audit_device_time / idx_audit_status_time / idx_audit_event_type` | 审计查询必带时间范围（分区裁剪），时间列放复合索引末位 |
| 工单超时扫描（定时任务扫过期 PENDING） | 后台每分钟 | `idx_tickets_pending_expire (expire_at) WHERE status='PENDING'` | 部分索引只覆盖活跃工单，扫描集极小 |
| 工单按租户/状态查询（工单中心） | 中 | `idx_tickets_tenant_status (tenant_id, status)` | 控制台列表与计数 |
| 审批人待办查询 | 中 | `idx_steps_approver_pending (approver_id) WHERE status='PENDING'` | 待办列表 |
| API Key 鉴权命中（每次 Agent 调用） | 极高 | `uq_api_keys_hash (key_hash)` | 哈希唯一索引 O(log n) 命中；鉴权结果进 Valkey 短缓存 |
| 设备心跳批量落盘 | 后台 | 无新增索引 | 按 id 主键 UPDATE，批量语句 |
| 计量按租户/类型/时间聚合（账单） | V1.5 起 | `idx_usage_tenant_type_time (tenant_id, event_type, occurred_at)` | 月度账单聚合扫描 |

索引纪律：写入热点表（audit_logs、usage_events）控制索引数量，每个分区独立维护索引带来批量写入成本，因此分区表只保留上述 5 个必要索引；`adc_devices.device_code` 全局唯一索引覆盖 FR-011 重复码回滚；`metadata`、`arguments`、`request_params` 等 JSONB 字段**故意不加 GIN 索引**（查询模式是整值取出而非键内检索），避免写入放大；若 V1.5 出现"按参数内容检索审计"需求，再评估表达式索引。

索引代价说明：`adc_audit_logs` 的 5 个索引使写入放大约 1.5~2 倍，但审计写入已异步化（ADR-06），不占调用主链路时延，属于可接受的换取；`adc_devices` 两张部分索引随设备注册低频更新，代价可忽略。查询性能验证方法：上线前用 3000 万行审计数据做 EXPLAIN ANALYZE 基线，多条件筛选须命中分区裁剪与复合索引，禁止出现顺序扫描（导出场景除外）。

## 5. 分区与归档

### 5.1 按月分区策略

`adc_audit_logs` 按 `created_at` 按月 RANGE 分区。分区边界用带时区的月首零点（`+08` 对齐业务日），使"按月导出、按月清理"与业务日历一致。

分区维护采用两条腿：**预建分区**（提前建未来 2 个月）与 **DEFAULT 兜底分区**（未预建时不丢数据）。预建分区由两个机制之一驱动：

1. 优先：`pg_partman` 扩展自动管理（若私有化部署允许扩展）；pg_partman 不可用时回退到 `pg_cron` 调用的建表函数。
2. 兜底：部署不支持任何扩展的离线环境，由 Go 后台任务（复用定时器基础设施）每月执行等价的 CREATE TABLE 语句。

```sql
-- 预建下月分区（pg_cron 每月 25 号执行；%s 为下月）
CREATE TABLE adc_audit_logs_2026_11 PARTITION OF adc_audit_logs
    FOR VALUES FROM ('2026-11-01 00:00:00+08') TO ('2026-12-01 00:00:00+08');
```

### 5.2 180 天归档清理

NFR-006 要求审计留存不少于 180 天。清理策略：**先 DETACH 再 DROP**，保证清理过程不阻塞写入、可观察可回退：

```sql
-- 每月 1 号，清理 180 天前的分区（如 2026-02 及更早）
ALTER TABLE adc_audit_logs DETACH PARTITION adc_audit_logs_2026_02;
-- 确认无误后（保留 7 天观察期）
DROP TABLE adc_audit_logs_2026_02;
```

合规客户（等保/私有化）要求更长的，通过配置项 `audit_retention_days` 覆盖 180 天默认值；如需长期留证，在 DETACH 后经 `pg_dump` 导出该分区为归档文件再 DROP。清理任务须写 `event_type='admin_op'` 的审计记录（谁、何时、清理了哪个分区、多少行）。

### 5.3 append-only 双保险

- 数据库权限：应用账号 `adc_app` 对 `adc_audit_logs` 仅 GRANT INSERT、SELECT，REVOKE UPDATE/DELETE/TRUNCATE；管理账号 `adc_admin` 与 DBA 账号分离，密码分别托管（FR-013：任何角色修改删除审计日志被拒绝）。
- 应用层：写入链路（ADR-06：经 JetStream 异步落库）代码评审门禁禁止对审计表出现 UPDATE/DELETE；数据修正只能通过追加一条 `admin_op` 类型更正记录实现。
- 验证：季度渗透测试用例包含"尝试 UPDATE 审计表必须失败"（FR-013 验收）。

### 5.4 容量与清理监控

- 监控指标：总表行数、最老分区、单分区大小、DEFAULT 分区行数（非零说明预建任务失效，立即告警）。
- 清理安全阀：DROP 前必须确认该分区 detached 且已过留存期；清理任务单次只处理 1 个分区，失败即停止当日任务并告警。
- 归档选项：等保三级客户（NFR-005）可能要求更长留存，通过 `audit_retention_days` 按租户部署配置覆盖；导出归档文件以 `pg_dump -Fc` 单分区导出，附行数校验。

## 6. 并发与一致性

### 6.1 审批工单防双判（SEC-11）

工单决策（同意/拒绝/过期）必须是单语句条件原子更新，用"状态+过期"双条件把判定与变更合并进一个原子操作，杜绝读-改-写竞态：

```sql
-- 审批同意：仅当仍为 PENDING 且未过期时生效；affected=1 才算成功
UPDATE adc_approval_tickets
   SET status = 'APPROVED',
       approver_id = $2, approver_name = $3, comment = $4,
       decided_at = now(), version = version + 1, updated_at = now()
 WHERE id = $1 AND status = 'PENDING' AND expires_at > now();
-- 应用层检查受影响行数：0 行 => 已被并发处理或已过期，返回"工单已处理"并落审计
```

```sql
-- 定时任务扫描过期（FR-005 默认 5 分钟），同样原子更新
UPDATE adc_approval_tickets
   SET status = 'EXPIRED', updated_at = now(), version = version + 1
 WHERE id IN (SELECT id FROM adc_approval_tickets
               WHERE status = 'PENDING' AND expires_at <= now()
               ORDER BY expires_at LIMIT 100 FOR UPDATE SKIP LOCKED);
```

三层防线：

1. **条件更新原子性**：`WHERE status='PENDING' AND expires_at > now()` 依赖行级锁，两个并发回调串行执行，第二个受影响行数为 0，天然只有一判生效。
2. **乐观锁兜底**：所有更新携带 `version` 校验（`WHERE version=$old`），防止未来引入读-改-写路径时退化。
3. **重复工单防抖**：`uq_tickets_pending_dedup (device_id, tool_name, params_hash) WHERE status='PENDING'` 保证同一设备同一工具同一参数只存在一个在途工单；INSERT 冲突时返回已有工单，防 Agent 重试刷工单。

审批决策的审计留痕与工单更新同事务提交，保证"有决策必有留痕"。

### 6.2 配额扣减的并发处理

配额权威账本在 `adc_tenants`（quota_* 与 used_* 计数），扣减用条件原子更新防超卖：

```sql
-- 设备注册配额扣减：超限时返回 0 行，事务回滚
UPDATE adc_tenants
   SET used_devices = used_devices + 1, updated_at = now()
 WHERE id = $1 AND used_devices < quota_devices AND status = 'ACTIVE';
```

热路径（调用次数）不做每调用一次 UPDATE：调用计数走 Valkey 计数器（SEC-12 限流同一计数器），后台每分钟批量聚合进 PG（`used_calls_month` 原子累加），与 FR-016"配额扣减与计量异步解耦、最终一致"对齐。对账机制：`adc_usage_events` 按 `occurred_at` 月度聚合结果必须与 `used_calls_month` 一致，差异超过阈值告警。停用租户（SUSPENDED）即时踢线并批量作废 PENDING 工单（FR-008 异常）。

### 6.3 幂等设计

| 场景 | 幂等键 | 机制 |
|---|---|---|
| 审计写入（ADR-06 JetStream 至少一次投递） | `request_id`（每次工具调用/审批决策生成） | 唯一索引 `uq_audit_request_id`，冲突则跳过 |
| 计量埋点（FR-016 网络抖动重试） | `idempotency_key`（生产者生成 UUID） | 唯一索引 `uq_usage_idempotency` |
| 重复审批工单（Agent 重试） | `params_hash` | 部分唯一索引，冲突返回已有工单 |
| 工具同步（设备上报） | `(device_id, tool_name)` 唯一约束 | upsert `ON CONFLICT ... DO UPDATE`，以 schema_version 递增判定覆盖 |

### 6.4 事务边界约定

- 工单创建事务：写入工单 + 第一步审批步骤 + 投递通知记录三行同一事务；通知实际推送在事务提交后异步执行（避免事务内等外部渠道，FR-005 卡片 30 秒时延）。
- 审批决策事务：条件 UPDATE 工单 + 更新当前步骤 + 写 audit_logs（approval_decision）同事务；指令下发动作在事务提交后触发，决策落库失败则不执行指令。
- 设备注册事务：INSERT 设备 + 配额条件 UPDATE 同事务；配额扣减失败整体回滚，返回明确配额错误（FR-008）。
- 审计写入：独立小事务批量提交（ADR-06 异步链路，每批数百行），与业务事务解耦，失败重投不阻塞主链路。
- 跨 PG/Valkey 一致性：心跳、限流、唤醒消息等 Valkey 操作全部是"尽力而为"，先 PG 后 Valkey，PG 失败则不写 Valkey；反向依赖（如工单创建后写 Valkey 唤醒通道失败）由重试与定时兜底扫描（6.1 超时扫描）收敛。

### 6.5 租户删除与数据生命周期

租户删除执行 FR-008 的 7 天冷静期，分两个阶段：

1. 冷静期（DELETING）：租户状态置 DELETING，所有 API Key 即时吊销、设备全部 FROZEN 并踢下线、PENDING 工单批量原子更新为 EXPIRED、停止接入新连接。冷静期内可恢复（回 ACTIVE）。
2. 正式删除（DELETED）：到期后由定时任务执行：软删除用户/分组/设备（置 deleted_at，凭证哈希清零）、删除 user_roles、审计与计量与工单永久留存（合规留痕，180 天自然清理）。单租户操作分批执行，每批事务内限 1000 行，避免长事务锁库。

软删除与不可删数据的分野由此明确：台账类可软删（保留业务语义），留痕类（审计/工单/计量/通知）永不删除，只走留存期清理。

## 7. 迁移与演进

### 7.1 迁移工具选择

推荐 **golang-migrate**（理由：与 Go 技术栈同源、纯 SQL 迁移文件、嵌入式迁移支持私有化离线交付、版本表简单可审计）。放弃 goose 的理由：goose 的 Go 函数式迁移会诱导把业务逻辑写进迁移，且其 CLI 与环境变量耦合较重；ADC 的迁移全部是声明式 DDL，golang-migrate 的纯 SQL 纪律更匹配。

```bash
# 迁移文件命名（版本号单调递增，禁止复用）
migrations/000001_init_schema.up.sql
migrations/000001_init_schema.down.sql
migrations/000002_audit_partition_2026_09.up.sql
```

### 7.2 迁移纪律

- 只向前：生产环境禁止执行 down 迁移；出错用新的 up 迁移修正（expand-contract）。
- 不可逆迁移禁止：生产分支禁止出现 DROP COLUMN、DROP TABLE、修改列类型等破坏性语句；改列走"加新列→双写→切换读→清理"四步，每步一个版本。
- 加列必须可空或带默认值：避免大表 rewrite 锁表；带默认值的加列在 PG 11+ 是元数据级操作，但禁止 `DEFAULT volatile_function()`。
- 单版本单逻辑：一次迁移只做一件事；迁移与代码同 PR 评审，DBA 角色审批。
- 大表 DDL 窗口：audit_logs 分区表上的索引变更在低峰执行；分区内建索引用 `CREATE INDEX CONCURRENTLY`。
- 基线快照：每季度把全部 up 迁移压缩为基线 SQL 一次（避免数百个迁移文件的启动成本），旧文件归档。

### 7.3 数据初始化与种子数据

- 平台预置角色（adc_roles is_system=TRUE）：PLATFORM_ADMIN、TENANT_ADMIN、APPROVER、AUDITOR、DEVELOPER 五类，随迁移脚本以确定性 ID（固定 UUID）插入，保证多环境一致。
- 首个平台管理员账号由部署引导流程创建（一次性引导令牌），不随迁移脚本写入任何凭证。
- CE 与 EE 迁移分层：EE 专属表（adc_approval_steps 等）的迁移文件放入 ee 迁移目录，CE 独立部署时按 seam 装配跳过（ADR-14），保证 CE 可独立运行。

### 7.4 V1.5 预留字段说明

V1.0 建表即预留、V1.5 启用的字段：`adc_tenants` 的 quota_* 与 used_*（计费对账）、`adc_usage_events` 整表（FR-016 埋点，V1.0 已开始写入但仅用于对账与看板，不计费）、`adc_devices` 的 mcp_endpoint/binding_token_hash（A 类设备，FR-021 阶段 2 起）、`adc_approval_steps`（FR-007 多级审批 EE 特性，CE 单级时该表为空）、`adc_device_tools.annotations`（FR-023 多语言工具描述覆盖层）。原则：**表结构一次到位，业务逻辑分批启用**，避免 V1.5 大表重构。

## 8. 备份与恢复

### 8.1 备份策略

V1.0 部署形态为单实例 PG + 可选主备（ADR-09 私有化为 Compose 单机）。备份组合：

1. **物理全量备份**：每日一次 `pg_basebackup -Fp -X stream -c fast -Z zstd`，保留 14 天；同时每日 `pg_dump -Fc` 逻辑备份小库（小于 10 GB）作二次保险。
2. **WAL 连续归档**：`archive_mode=on` + `archive_command` 推送到异地对象存储（或私有化环境的备份目录），`wal_keep_size` 与归档互为补充；PITR 窗口 = 归档留存 30 天。
3. **主备流复制**（可选）：`wal_level=replica` 下异步备机，提供读容灾与快速切换，不作为备份替代（误删数据会被同步复制）。

### 8.2 RPO/RTO 目标与验证

| 指标 | 目标 | 依据 | 达成手段 |
|---|---|---|---|
| RPO | 不超过 5 分钟 | NFR-001 | WAL 归档到远端，归档延迟监控小于 5 分钟 |
| RTO | 不超过 30 分钟 | NFR-001 | 最近全量备份 + WAL 回放；主备切换场景 RTO 小于 1 分钟 |

验证方法（不演练的备份不是备份）：

- 每季度一次恢复演练：在 staging 环境用最近备份 + 归档 WAL 做 PITR 恢复，验证到演练时刻的 RPO 实测值；随机抽取 3 个租户比对审计行数与 usage_events 聚合值。
- 每次备份作业后校验：`pg_verifybackup` 校验全量备份完整性；归档文件带 checksum。
- 演练结果记录进 `adc_audit_logs`（admin_op 事件），形成"备份-演练-留痕"闭环。

### 8.3 私有化交付的备份变体（ADR-09）

私有化部署（Docker Compose 单机）由客户运维执行备份，交付物必须包含：备份脚本（pg_basebackup 到挂载卷）、WAL 归档开关模板、一键恢复手册与演练清单。离线环境无对象存储时归档到独立磁盘并做每日完整性检查；交付验收标准包含"在客户环境完成一次恢复演练并通过比对"（implementation-delivery-expert 验收联动）。

### 8.4 Python Agent 面数据预留（方案 A，ADR-20）

Python Agent 面（V1.0 最小集：评测工具链）不需要新增表；V1.5 完整集（LLM 网关/四 Agent 编排/A2A，FR-012/022/024）预留一张表，V1.0 不建、V1.5 建表前经 openspec 变更补充 DDL 并纳入本说明书：

| 预留表 | 用途 | 关键字段（草案） | 归属版本 |
|--------|------|------------------|----------|
| adc_agent_tasks | 内部多 Agent 编排任务（Planner/设备选择/执行/HITL 审批流水线）状态与结果 | task_id、tenant_id、agent_id、task_type、status、graph_trace、device_targets、input/output、created_at/updated_at、expires_at | V1.5 |

设计约束（V1.5 落地时遵守）：任务表与审批工单（adc_approval_tickets）通过 task_id 关联而非内嵌审批；任务表只追加不覆盖（编排可回放）；分区策略同审计表按月分区（任务量大）；评测结果落 adc_usage_events 旁的新表或复用，由 V1.5 变更评审决定。
