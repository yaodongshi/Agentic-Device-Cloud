# ADC 部署与交付方案（design/60）

> 视角：DevOps 专家
> 依据基线：doc/05（ADR-09 私有化部署形态、ADR-13 Valkey、ADR-01 控制面/数据面拆分、ADR-02 NATS JetStream、ADR-12 三仓分层）、doc/03 PRD（NFR-001 可用性、NFR-002 规模、NFR-005 合规、NFR-006 日志可观测）、design/70（方案 A：Go 数据面 + Python Agent 面，uv 依赖管理）

### 1.3 配置管理（环境即代码）

环境差异只经配置注入，制品一次构建多次部署，严禁在部署机上改代码或改镜像（devops-expert 铁律）。配置分层：

| 层 | 载体 | 内容 | 变更方式 |
|---|---|---|---|
| 构建参数 | `--build-arg` | 版本号、编译目标 | 流水线自动 |
| 环境变量 | `.env`（安装时生成） | `ADC_VERSION`、宿主端口、时区、License 路径 | 安装/升级脚本写 |
| 敏感配置 | Compose `secrets` | 口令、JWT 密钥、证书私钥 | `rotate-secrets.sh` 轮转 |
| 非敏感配置 | 应用配置卷（只读挂载） | 限流参数、通知渠道、日志级别 | 版本化配置仓库 |

配置漂移检测：`docker compose config` 输出与交付清单 diff，纳入升级脚本前置校验；手工改过的环境视为负债，一律重装收敛。

容量推算过程（1000 台设备 V1.0 验证基线，均为假设值，压测后修正）：

| 资源项 | 推算 | 备注 |
|---|---|---|
| 设备长连接内存 | 1000 连接 x 约 1MB 会话缓冲 = 1GB | goroutine + 读缓冲 |
| Agent API 并发 | 峰值 100 并发 x 单请求 10MB = 1GB | 工具聚合瞬时峰值 |
| PostgreSQL 缓冲 | shared_buffers 2GB + 连接内存 | 审计写入为主 |
| Valkey | 心跳键 1000 个 + 限流桶，约 100MB | 预留 1GB |
| 审计存储 | 日调用 1 万次 x 1KB x 180 天 = 约 2GB | 分区表按月清理 |
| py-agent（V1.5 完整集） | 常驻 1-2GB（V1.0 最小集 512MB，CLI 不常驻） | 评测/Agent 面服务 |
| 合计 | V1.0 最小集约 8-10GB；V1.5 完整集约 10-12GB | V1.0 在 16G 主机 60% 水位线内；V1.5 逼近红线，需升配 24GB 或转拆分形态（ADR-01 演进路径内） |

审计留存 180 天为下限（NFR-006），数据盘预算按 500GB 起步，按租户实际调用量季度校准。

## 2. 容器化方案

### 2.1 Dockerfile 策略（Go 服务统一模板）

所有 Go 服务（gateway/admin/approval）使用同一多阶段构建模板：golang 构建层 + distroless 运行层，静态编译（CGO_ENABLED=0），非 root 运行，健康检查用内嵌子命令（distroless 无 shell，不能用 shell 形式 HEALTHCHECK）。其中 gateway 为统一 API 网关（Go 实现，前端唯一入口），职责含路由、鉴权透传、限流与契约校验（见 3.1 与 3.4）；Python Agent 面（py-agent）采用独立模板，见 2.2。

```dockerfile
# ce/ 与 ee/ 共用模板，ARG 区分版本
FROM --platform=$BUILDPLATFORM golang:1.24-alpine AS build
ARG TARGETOS TARGETARCH SERVICE
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -trimpath -ldflags="-s -w -X main.version=${VERSION}" \
    -o /out/${SERVICE} ./cmd/${SERVICE}

FROM gcr.io/distroless/static-debian12:nonroot
ARG SERVICE
COPY --from=build /out/${SERVICE} /app/${SERVICE}
USER 65532:65532
EXPOSE 8080
HEALTHCHECK --interval=15s --timeout=3s --retries=3 \
  CMD ["/app/gateway", "healthcheck"]
ENTRYPOINT ["/app/gateway"]
```

要点：
- `--platform=$BUILDPLATFORM` 配合 `TARGETOS/TARGETARCH` 自动变量，一条 buildx 命令产出双架构，无需改 Dockerfile（amd64/arm64 跨平台硬约束的构建实现）。
- 每个服务二进制内嵌 `healthcheck` 子命令（探测本地健康端点，退出码 0/1），distroless 下 exec 形式可直接执行。
- `static-debian12:nonroot` 为多架构镜像且带时区/CA 证书数据，信创 ARM（鲲鹏 920/飞腾 S2500）与 x86 海光/兆芯均可运行；`nonroot` 变体满足等保"最小权限运行"要求。
- 若个别组件需挂载私有 CA 证书（如企业内网 OIDC 对接），将证书卷挂载至容器内 `/etc/ssl/certs`（覆盖宿主私有 CA），镜像本身不再更换基础镜像，禁止退回 root 运行。
- 层缓存策略：`go.mod` 拷贝优先于源码拷贝（依赖层缓存），`go mod download` 与 `COPY . .` 分层，源码变更不重下依赖；构建缓存经 buildx cache-to/cache-from 注册表缓存，双架构各自独立缓存。

### 2.2 py-agent（Python Agent 面）镜像构建策略

Python 面采用 uv 管理依赖（uv.lock 冻结版本，双架构与离线可复现），镜像模板如下：

```dockerfile
# ce/ 与 ee/ 共用模板，ARG 区分版本；py-agent 为 FastAPI/uvicorn 服务
FROM --platform=$BUILDPLATFORM ghcr.io/astral-sh/uv:latest AS uv
FROM --platform=$BUILDPLATFORM python:3.14-slim AS build
COPY --from=uv /uv /uvx /bin/
WORKDIR /src
COPY uv.lock pyproject.toml ./
COPY app ./app
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev --no-editable

FROM python:3.14-slim
ENV PATH="/src/.venv/bin:$PATH" \
    UV_COMPILE_BYTECODE=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    TZ=Asia/Shanghai
COPY --from=build /src/.venv /src/.venv
COPY --from=build /src/app /src/app
RUN useradd --system --uid 10001 adc
USER 10001:10001
WORKDIR /src
EXPOSE 8085
HEALTHCHECK --interval=15s --timeout=3s --retries=3 \
  CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8085/healthz', timeout=3)"]
ENTRYPOINT ["python", "-m", "adc_agent"]
```

要点：
- uv 二进制经多阶段从官方镜像拷贝（`ghcr.io/astral-sh/uv`），构建层与运行层均不落全局 pip；依赖全部落在 `.venv` 随层复制。`--frozen` 强制 uv.lock 一致、`--no-dev` 剥离开发依赖（ruff/mypy/pytest 不入镜像）、`--no-editable` 产出可复制产物；`uv.lock` 先于源码拷贝，依赖层缓存（uv.lock 不变不重下）。
- 非 root（UID 10001）运行，符合等保最小权限；slim 自带 urllib，HEALTHCHECK 用 exec 形式直连 `/healthz`（探针语义见 6.4，与 Go 服务对齐）。
- 双架构（amd64/arm64）：`python:3.14-slim` 与 uv 官方镜像均为多架构，核心依赖（pydantic-core/cryptography/uvloop 等）arm64 预编译 wheel 齐备【事实：design/70 2.5】；构建走 2.6 同一 buildx 流水线（amd64 构建机 QEMU 或方案 B 双构建机原生，见 2.6/5.4）。
- wheelhouse 离线固化流程（有网构建机 → 离线交付）：
  1. 有网构建机：`uv sync --frozen --no-dev` 后执行 `uv cache export > wheelhouse/index.json`，将 `uv.lock` 与 uv 缓存（wheel 目录）一并打包为 `py-agent-wheelhouse-${VERSION}-${PYTHON_TAG}.tar.gz`；
  2. 离线机（客户自建镜像/二次开发场景）：解包后 `uv sync --offline --frozen --no-dev`，全部依赖命中本地缓存，零外网；
  3. wheelhouse 按 `平台（amd64/arm64）x Python 版本 x libc` 分目录维护，交付侧按客户架构精确选择；离线交付包内镜像已含依赖层，wheelhouse 供重建与二次开发（见 4.1）。
- 部署形态：V1.0 最小集为评测工具链（CLI 形态，`python -m adc_agent.eval`，不常驻主服务）；V1.5 完整服务（uvicorn 常驻）经 `ADC_PYAGENT_MODE=full` 开关启用（见 3.3）。

### 2.6 buildx 多架构构建流水线

```bash
# 一次性注册 QEMU（每台构建机一次）
docker run --privileged --rm tonistiigi/binfmt --install all

# 构建并推送三服务（以 gateway 为例，amd64+arm64 双架构硬约束）
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  --build-arg SERVICE=gateway --build-arg VERSION=v1.0.0 \
  -t ghcr.io/adc-io/gateway:v1.0.0 -t ghcr.io/adc-io/gateway:latest \
  --sbom=true --provenance=mode=max \
  --push -f build/Dockerfile.go .

# py-agent（Python 面）同一流水线，双架构硬约束不变
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  --build-arg VERSION=v1.0.0 \
  -t ghcr.io/adc-io/py-agent:v1.0.0 -t ghcr.io/adc-io/py-agent:latest \
  --sbom=true --provenance=mode=max \
  --push -f build/Dockerfile.py .
```

信创说明：arm64 镜像目标为鲲鹏/飞腾等 ARM 信创服务器，运行侧无额外要求；构建侧若自建机为 arm64（如信创开发机），QEMU 反方向模拟 amd64 即可，构建时间约慢 2-3 倍，双架构构建建议在 amd64 构建机执行。py-agent 依赖层经 uv.lock 缓存（`uv.lock` 未变更时 `uv sync` 命中缓存层，不重下依赖）；若个别 Python 包无 arm64 预编译 wheel 需 QEMU 下编译且超时，改用方案 B 双构建机原生构建（5.4）。

| 网络 | 成员 | 用途 |
|---|---|---|
| adc-edge | nginx、gateway | 边缘入站唯一入口与反代（nginx 仅反代 gateway，不直连后端） |
| adc-internal | gateway、admin、approval、console、py-agent、postgres、valkey、nats | 服务间与存储，无宿主端口映射（网关内部可达各后端） |
| adc-obs（可选） | 各服务 + prometheus 等 | 指标与日志采集 |

规则：仅 nginx 有宿主端口映射（80/443）；仅 gateway 对外提供路由（设备/Agent/Admin/HITL 全经网关）；后端服务零宿主暴露；py-agent 仅入 `adc-internal`，仅网关可达（开发 profile 除外）；postgres/valkey/nats 零宿主暴露（开发 profile 除外）；`adc-internal` 禁止被外部网络 attach。

- 离线交付：`docker compose --profile airgap -f compose.yaml -f compose.airgap.yaml up -d`（镜像一律来自 docker load，无任何 pull）
- 开发：`docker compose --profile dev up -d`（宿主端口映射 postgres 5432/valkey 6379 便于调试，禁用生产 secret 文件，使用 .env.example）

### 3.4 nginx 边缘配置要点（路由与限流）

方案 A 规则：nginx 仅反代统一 API 网关（gateway），不再直连任何后端；路由、鉴权透传、限流、契约校验全部下沉到网关。

```nginx
# deploy/nginx.conf（片段）
upstream gateway_http  { server gateway:8080  max_fails=3 fail_timeout=30s; }

server {
  listen 443 ssl;
  ssl_certificate     /etc/nginx/certs/server.crt;
  ssl_certificate_key /etc/nginx/certs/server.key;
  client_max_body_size 4m;               # 呼应 SEC-19 body 限制
  limit_conn per_ip 50;

  # 长连接路由（设备隧道/Streamable HTTP），升级头必须透传
  location /v1/devices/ {
    proxy_pass http://gateway_http;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;            # 长任务与流式（ADR-10）
  }
  # Agent/Admin/HITL 等业务 API 全交网关：网关内部路由到
  # admin/approval/py-agent，并承担鉴权透传、限流、契约校验
  location /v1/        { proxy_pass http://gateway_http; }
  # 灰度期：/v2/agent/ 由网关指向新版 py-agent 实例，转正后合入 /v1/（见 4.4）
  location /v2/        { proxy_pass http://gateway_http; }
  location /            { root /usr/share/nginx/html; }
}
```

## 4. 私有化离线交付（air-gap）

### 4.1 离线镜像打包流程（save/load + 签名校验）

构建机（有网）产出：

```bash
# 1. 拉取客户架构对应的全部镜像（按客户架构精确选择 amd64 或 arm64）
for img in nginx gateway approval admin console py-agent postgres:16-alpine valkey/valkey:8-alpine; do
  docker pull ${img}
done

# 2. 单文件归档（含 SBOM 与 manifest）
docker save $(< image-list.txt) | gzip > adc-airgap-${VERSION}-${ARCH}.tar.gz
syft scan dir:adc-airgap-root -o spdx-json > sbom.spdx.json

# 3. cosign 对归档签名（交付包完整性校验）
cosign sign-blob --key cosign.key adc-airgap-${VERSION}-${ARCH}.tar.gz
```

Python 依赖离线组件：`py-agent-wheelhouse-${VERSION}-${ARCH}.tar.gz`（uv.lock + uv 缓存/wheel 目录，流程见 2.2）随包下发，供客户内网自建镜像或二次开发；交付包默认形态客户仅 `docker load` 镜像，镜像内已含 py-agent 依赖层。

交付清单 `manifest.json` 记录：镜像名/摘要/SBOM/签名/wheelhouse 包 sha256/安装脚本 sha256，任一不一致即中止安装。

客户内网执行（离线安装机）：

```bash
# 验签 + 解压 + load + 标记镜像名与仓库一致
cosign verify-blob --key adc-public.pem --signature adc-airgap-${VERSION}.sig \
  adc-airgap-${VERSION}-${ARCH}.tar.gz
gunzip -c adc-airgap-${VERSION}-${ARCH}.tar.gz | docker load
# load 后镜像摘要与 manifest.json 逐项比对，任一不符即中止安装
```

### 4.2 一键安装脚本

```bash
#!/usr/bin/env bash
# install.sh：离线交付入口，幂等可重入
set -euo pipefail
INSTALL_DIR=/opt/adc
# 1) 前置检查：Docker 版本、架构匹配（uname -m 与交付包 ARCH 比对）、磁盘、端口占用
# 2) 解包与验签（4.1 流程），manifest.json 摘要比对（含 wheelhouse 包 sha256，V1.5 完整集自建镜像时使用）
# 3) 生成 secrets（openssl rand 一次生成 pg_password/gateway_key/jwt_key 等）
# 4) 写 /opt/adc/.env（ADC_VERSION、宿主架构、时区 Asia/Shanghai、License 路径、ADC_PYAGENT_MODE）
# 5) docker compose --profile airgap -f compose.yaml -f compose.airgap.yaml up -d
# 6) 健康探测轮询（gateway/admin/py-agent /readyz 与 /healthz），全部就绪后输出管理台地址
# 7) 打印激活指引：上传 License 文件或输入离线激活码
```

安装编排顺序（dependencies 之外的显式时序）：postgres 健康 → valkey 健康 → 数据库迁移任务（一次性容器，跑完退出）→ gateway/approval/admin 拉起 → py-agent 拉起（完整集；最小集为 CLI 不常驻，仅校验镜像内评测工具可用）→ console/nginx 就绪 → 输出访问入口。迁移任务必须幂等（版本表记录已执行迁移号）。

### 4.3 License 激活与心跳计量（对接 design/31）

本方案仅固化交付侧契约，计量与计费口径以 design/31 为准：

- 激活：`adc-license-${CUSTOMER}.lic` 文件（含客户标识、设备数上限、到期时间、功能位），安装机经 `admin` 的 `/v1/license/activate` 上传，服务端用内置公钥验签后落库；离线激活码为 license 文件的 base64 压缩形态，支持 U 盘导入。
- 心跳计量：`admin` 内嵌计量模块，按日聚合设备在线数/调用量/审批量，生成签名心跳报文；在线环境推送至计量端点（可关闭），离线环境导出本地签名报告，客户回传用于续费对账。心跳失败不阻断业务，宽限期 30 天（假设值，design/31 可调）。
- 时钟防回拨：admin 记录本地最大时间戳，检测到回拨即告警并冻结激活状态，防止改系统时间绕过到期。
- 到期降级：到期后进入宽限期（只读告警，不中断设备连接），超宽限期停止 Agent API 写操作、保留数据面保活，客户数据永不清删。

### 4.4 升级与回滚流程

| 步骤 | 操作 | 说明 |
|---|---|---|
| 升级前 | 全量备份 + `docker compose config` 校验 + 记录当前镜像摘要 | 失败可回滚 |
| 升级 | 新镜像 load → 改 `ADC_VERSION` → `docker compose up -d` 滚动替换无状态服务 → postgres 执行向前兼容迁移（expand-contract，先加列后删列） | 数据库迁移必须向前兼容 |
| py-agent 升级（V1.5 起） | 新版镜像 load → 网关 `/v2/agent/` 灰度路由指向新实例（旧 `/v1/agent/` 保留）→ 冒烟通过后网关主路由切新版 → 保留一个版本窗口后清理旧版 | 网关路由与 py-agent 版本强绑定，回滚即回切网关路由配置，无需重建数据面 |
| 验证 | 健康探测 + 冒烟清单（设备重连、tools/list、一次免审调用、一次审批链路、评测工具链一次跑通） | 见第 9 章 checklist |
| 回滚 | 回切 `ADC_VERSION` → `docker compose up -d`；数据库回滚走反向迁移或快照恢复 | 回滚演练每季度一次 |
| 大版本 | PG 16 跨版本升级走 pg_dumpall 迁移到新数据卷，双卷并行后切流 | 禁止原地 pg_upgrade 后无验证 |

py-agent 与网关契约（工具 schema、MCP 协议版本）向后兼容；升级顺序固定为：先升网关（保持兼容旧 py-agent）→ 再灰度 py-agent（/v2/ 路径）→ 转正；回滚反向执行，禁止先降网关再降 py-agent。

发布窗口纪律：工厂产线白天不可中断，升级一律安排维护窗口（周末或夜班，与客户约定）；升级前 48 小时冻结变更；每个版本随包附 Release Notes 与升级影响面（数据库迁移、配置新增项、设备断连时长估计）。

```text
    → 私有化交付包构建（按客户架构与功能位定制）
```

制品晋升铁律：同一镜像摘要从 staging 原样升生产，禁止重新构建；staging 与生产差异仅存在于配置与密钥；晋升需双人审批（发布人 + 版本负责人），审批记录入审计。

### 5.6 Python 作业段（双语言矩阵）

双语言矩阵：Go 与 Python 两套作业在合入 main 与打 tag 时并行执行，门禁口径一致（静态检查/单测/双架构镜像/SBOM/签名），任一失败即阻断发布；版本 tag 同一来源，ce/ 流水线同时产出 Go 镜像、py-agent 镜像与 wheelhouse 制品（4.1 离线包组装依赖）。

```yaml
# .github/workflows/python.yml（预留骨架，方案 A：GitHub Actions）
jobs:
  python-ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - run: uv sync --frozen --no-dev
      - run: uv run ruff check . && uv run ruff format --check .
      - run: uv run mypy app
      - run: uv run pytest -m 'not e2e'
      - run: uv lock --check
      - run: |
          uv sync --frozen --no-dev --no-editable
          uv cache export > wheelhouse/index.json
          tar czf py-agent-wheelhouse-${GITHUB_REF_NAME}.tar.gz uv.lock wheelhouse
      - uses: docker/setup-buildx-action@v3
      - uses: docker/setup-qemu-action@v3
      - run: |
          docker buildx build --platform linux/amd64,linux/arm64 \
            -t ghcr.io/adc-io/py-agent:${{ github.ref_name }} \
            --sbom=true --push -f build/Dockerfile.py .
      - uses: aquasecurity/trivy-action@master
        with: {image: "ghcr.io/adc-io/py-agent:${{ github.ref_name }}", exit-code: "1"}
      - run: cosign sign ghcr.io/adc-io/py-agent:${{ github.ref_name }}
```

方案 B（5.4 自建 gitlab-runner）同样适用 Python：amd64/arm64 双构建机原生产出各自 wheel 缓存后合并 manifest；ruff/mypy/pytest 与架构无关只跑一次，镜像与 wheelhouse 双架构分开产出。V1.0 最小集（评测工具链 CLI）随 py-agent 镜像发布，不单独建服务镜像。

### 6.2 日志收集（结构化 JSON + 轮转）

- 全服务输出结构化 JSON 到 stdout（字段含 tenant_id、trace_id、event_time（Asia/Shanghai）、level），docker 日志驱动 `json-file` + max-size=50m + max-file=20 轮转；生产加 loki + promtail 聚合（obs profile）。
- py-agent（FastAPI/uvicorn）access log 与业务日志统一输出结构化 JSON（uvicorn json formatter + logging 配置），字段与 Go 侧一致，进入同一条 loki 聚合链路；/metrics 由 prometheus-client 暴露（见 6.1），trace_id 经请求头透传贯通网关到 py-agent。
- 审计日志（NFR-006）双通道：JetStream 异步落 PG 分区表（180 天留存）+ 不可变审计文件，禁止与运行日志混存；日志中零明文密钥（SEC-25）。
- trace_id 贯通设备接入、工具调用、HITL 工单与审计（PRD 5 章埋点规范）；调用链追踪经 langfuse（阶段 4 全量集成）。

```json
{"level":"info","event":"tool_call_end","tenant_id":"t-01","trace_id":"a1b2c3",
 "device_id":"cnc-07","tool":"set_spindle_speed","risk_level":2,
 "hitl_ticket":"HITL-20260814-001","result":"ok","duration_ms":340,
 "event_time":"2026-08-14T10:31:05+08:00"}
```

日志样本规范：所有事件含 tenant_id、trace_id、event_time（Asia/Shanghai）；敏感字段（凭证、webhook key、审批人手机号）一律脱敏输出；埋点失败不影响主链路（PRD FR-016）。

### 6.3 告警规则表

| 级别 | 规则 | 阈值 | 处置 |
|---|---|---|---|
| P1 | 网关进程/心跳丢失 | 5 分钟无指标 | 立即呼叫 + 自动重启兜底 + 回滚评估 |
| P1 | 设备在线数骤降 | 10 分钟内降 30% | 呼叫 + 检查链路与宿主机 |
| P1 | PG/Valkey 不可达 | readiness 失败 | 呼叫 + 按 RTO 30 分钟执行恢复手册 |
| P2 | 网关后端依赖不可达（py-agent/admin/approval） | readiness 失败持续 5 分钟 | 值班处理 + 网关路由降级（跳过异常后端） |
| P2 | HITL 推送失败率（SEC-18） | 5 分钟内失败超 10% | 值班处理 + 降级短信提醒 |
| P2 | JetStream 积压 | pending 超 1000 持续 10 分钟 | 值班排查消费端 |
| P2 | CPU/内存水位 | 超 80% 持续 15 分钟 | 扩容或转拆分形态 |
| P3 | License 心跳失败/到期临近 | 连续失败 3 次/剩余 30 天 | 通知客户成功与支持 |
| P3 | 备份失败 | 任意一次 | 次日修复确认 |
| P3 | 日志轮转异常/磁盘 85% | 持续 30 分钟 | 清理与扩容 |

每条告警配 runbook 链接与归属人；无 runbook 的告警直接删除（告警必须可行动）。

### 6.4 探针设计

| 探针 | 路径 | 语义 | 失败动作 |
|---|---|---|---|
| startup | /readyz（带依赖等待） | 启动就绪（PG/Valkey 连接、迁移完成） | 延长启动窗口，不杀进程 |
| readiness | /readyz | 可接流量 | 摘除流量（nginx upstream 剔除） |
| liveness | /healthz | 进程存活（无死锁、事件循环在转） | 重启容器 |
| 设备心跳 | 应用层（SEC-14 续期） | 设备在线判定，last_heartbeat 更新 | 台账标离线（不可误杀长连接） |

nginx upstream 以 readiness 为准动态剔除不健康实例，实现单机滚动升级零中断。

### 6.5 监控大盘与排障入口

- 核心大盘（Grafana）：设备在线趋势、Agent 调用 QPS 与 P95/P99、网关路由命中与 5xx 分布、py-agent 调用量与评测统计、HITL 工单漏斗、审批时效分布、LLM Token 消耗（计量对齐 design/31）、资源水位。
- 排障路径固化：告警 → runbook → trace_id 关联（langfuse 调用链 + 结构化日志检索）→ 审计记录交叉验证；单机环境自带 grafana（obs profile），私有化交付默认包含只读大盘。
- 成本控制：日志按租户/事件类型分 retention（运行日志 14 天、审计 180 天双轨），控制存储增长；指标保留 30 天下采样。

## 7. 安全加固

### 7.1 TLS 证书管理

- 拓扑：TLS 终结于 nginx（443）；设备面 WSS/Streamable HTTP 与 Agent API 全走 nginx（SEC-05）；postgres/valkey 内部通道各自 TLS（verify-full / --tls，SEC-06）。
- 私有化/离线：随包内置内部 CA（安装脚本签发服务证书 + 客户端证书，90 天轮转，cron 自动续签）；SaaS：Let's Encrypt + 自动续签。轮转期间双证书并载，0 停机。
- 设备 mTLS 为阶段 3 终态（ADR-04），当前证书体系预留 CA 分层（根 CA 离线保管、中间 CA 签发设备证书）。

### 7.2 Secret 注入规范

- 零明文：仓库、镜像、日志、环境变量、进程参数不得出现密钥（SEC-13/25）；生产经 Compose `secrets` 文件挂载 `/run/secrets/*`，KMS/Vault 为 SaaS 形态升级路径。
- 权限：secrets 文件宿主 600、容器内 400；密钥长度规范（JWT 512bit、pg_password 32 字节随机、Valkey ACL 每服务独立账号最小权限，SEC-06）。
- 轮转：JWT 密钥/数据库口令每 90 天轮转；轮转脚本化（`rotate-secrets.sh`）并纳入升级包。

### 7.3 网络隔离与最小端口暴露

- 仅 nginx 对宿主开 80/443（开发 profile 另议）；postgres/valkey/nats 零宿主映射；Valkey ACL 按 gateway/approval/admin/py-agent 分账号 + TLS 端口，明文端口关闭。
- nginx 层：body 大小限制、连接限流、每租户/每 Agent 限流透传（SEC-12 网关中间件兜底）、CheckOrigin 白名单（SEC-04）。

### 7.4 容器运行时加固

- 镜像层：distroless 最小攻击面；无包管理器、无 shell；非 root 运行（USER 65532）；只读根文件系统（read_only: true，除数据卷外）；capabilities 全 drop。
- 供应链：镜像签名（cosign）校验进部署前置；registry 镜像拉取摘要锁定（`image@sha256:` 而非浮动 tag）；依赖漏洞扫描结果随交付包提供给客户。
- 宿主机：仅安装 Docker 与必要工具；ssh 仅密钥登录；防火墙白名单；生产宿主不跑构建（QEMU/特权容器只在构建机）。

### 7.5 等保相关配置项（V1.5 测评对齐）

| 项 | 配置 |
|---|---|
| 身份鉴别 | 管理员 OIDC/SSO + MFA（阶段 3）；登录失败锁定（5 次锁 30 分钟） |
| 访问控制 | RBAC 最小权限；会话超时 30 分钟 |
| 安全审计 | 审计留存 180 天（NFR-006）；审计文件 append-only、不可抵赖（SEC-08/21） |
| 入侵防范 | 宿主防火墙（ufw/firewalld 白名单）；镜像漏洞扫描门禁（第 5 章） |
| 恶意代码 | 客户内网杀毒扫描交付包；SBOM 随包 |
| 时间同步 | chrony 对时（License 心跳依赖正确时钟） |
| 备份恢复 | 第 8 章方案 + 每年一次恢复演练记录 |
| 安全运维 | 漏洞公告订阅（PostgreSQL/Valkey/Nginx 上游 CVE 监测），高危 CVE 48 小时内评估并出热修包；补丁发布走同一门禁流水线 |

等保差距整改与测评安排：V1.0 完成等保差距分析（PRD 发布标准），V1.5 前通过三级测评（NFR-005）；本方案第 7 章各项配置即为整改落地载体，部署包内附《安全基线配置核查表》供测评机构逐项核对。

## 8. 备份与恢复

### 8.1 PostgreSQL 备份策略（RPO ≤ 5 分钟）

- 连续归档：`archive_mode=on` + `archive_timeout=300`（WAL 每 5 分钟强制切段归档到 adc-backup 卷），RPO ≤ 5 分钟达成（NFR-001）。
- 全量：每日 02:00 `pg_dump -Fc` 全量 + 每周日 `pg_basebackup`（供时间点恢复基线）；备份文件 sha256 校验 + 异地 rsync（异机或 NFS）。
- Valkey 不备份（纯缓存语义，ADR-05 审批已落 PG）；JetStream 流随 PG 窗口快照。

### 8.2 恢复演练（RTO ≤ 30 分钟）

```bash
# 演练脚本 restore-drill.sh（每季度执行）
# 1) 在演练机 docker compose --profile ee up（空卷）
# 2) 还原最近全量 + 重放 WAL 至目标时间点
pg_restore -d adc adc-full-latest.dump
# 3) 冒烟清单（第 9 章）全过
# 4) 记录实际耗时，目标 ≤ 30 分钟
```

RTO 达成要点：单机 Compose 部署简化恢复链（无集群协调）；无状态服务恢复即拉起；设备断线重连（退避 + 踢旧连接，SEC-15）自动重建会话，无需人工干预。

### 8.3 故障场景演练矩阵

| 场景 | 演练频率 | 验证目标 |
|---|---|---|
| PG 数据卷损坏恢复 | 每季度 | RTO ≤ 30 分钟、WAL 归档完整 |
| 单服务崩溃自动重启 | 每月 | P1 告警触发、服务自愈、设备重连 |
| 证书到期轮转 | 每季度 | 0 停机轮转、旧证书清理 |
| 误升级回滚 | 每季度 | 回滚流程与向前兼容迁移 |
| 宿主机宕机切换 | 每半年 | 拆分形态下数据面/控制面互不影响 |
| 时钟漂移（离线环境） | 每季度 | License 心跳告警与对时恢复 |

演练均留书面记录（操作人、耗时、偏差、整改项），作为等保"应急预案与演练"测评证据（NFR-005）。

## 9. 风险与 Checklist

### 9.1 上线检查清单（每环境必过）

1. 双架构确认：宿主 `uname -m` 与镜像架构匹配，manifest 检查双架构在位
2. 端口扫描：仅 80/443 暴露
3. 密钥检查：secrets 全量生成、权限 400/600、仓库与镜像内 gitleaks 零命中
4. TLS：证书有效、轮转 cron 生效、Valkey/PG 内部 TLS 握手成功
5. 探针：全部服务（含 py-agent /healthz）healthy/ready
6. 冒烟链路：mock 设备注册 → tools/list → 免审调用 → 高危调用 HITL → 审批通过 → 设备执行 → 审计可查 → 评测工具链一次跑通（py-agent 最小集）
7. 备份：全量备份已生成、WAL 归档滚动正常
8. 监控：Prometheus 指标采集、P1 告警通道验证（触发一次测试告警）
9. License：激活状态正确、心跳生成、到期时间正确
10. 回滚包：上一版本镜像摘要与迁移脚本在手

### 9.2 回滚手册要点

- 触发条件：升级后冒烟清单任一失败、P1 告警且根因指向新版本、审批链路异常（高危拦截率下降）。
- 动作：回切 `ADC_VERSION` → 无状态服务秒级回滚；数据库向前兼容迁移保证旧代码可读新数据（expand-contract）；紧急兜底为快照恢复（RTO 30 分钟）。
- 铁律：数据库迁移不随回滚强制逆向；设备连接风暴用重连退避与连接数上限压制（PRD 风险 6）；回滚后 24 小时观察窗口。
- 发布值守：升级后 2 小时内发布人在线值守，盯着 P1 告警与设备在线数曲线；异常 15 分钟内未定位即回滚，不恋战。

### 9.3 跨平台兼容性验收要点（硬约束专项）

1. amd64 与 arm64 两套镜像在门禁中同时构建成功，manifest list 双架构在位（缺任一架构阻断发布）
2. 信创验证机清单：麒麟 V10 SP3（arm64）、统信 UOS V20（amd64 或 arm64）、OpenEuler 22.03（x86）各过一遍安装脚本与冒烟清单
3. 开发环境：macOS（arm64）与 Windows WSL2（amd64）跑通 `--profile dev` 全链路，作为开发者入门门槛
4. 时间与时区：容器内 TZ=Asia/Shanghai 一致性校验（审计事件时间戳正确）
5. 离线交付包按客户架构单架构打包，安装脚本显式校验 `uname -m` 与包架构匹配，拒绝跨架构误装
