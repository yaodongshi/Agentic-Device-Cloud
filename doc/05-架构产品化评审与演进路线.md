# ADC 架构产品化评审与演进路线

> 评审对象：《Agentic Device Cloud (ADC) 技术架构与系统实现方案》（doc/Agentic Device Cloud.md，下称"原方案"）
> 评审视角：架构专家 + 安全专家 + 开源专家（STRIDE 威胁建模 + 产品化差距分析 + Open Core 许可证合规评审）
> 共享事实基线：AI 原生设备编排与治理平台；首发离散制造；SaaS+私有化双形态；中国 + 全球双主场（全栈 i18n、英文优先社区）；单租户 100-1000 设备、平台 1 万在线设备起步、网关 99.9% SLA（以上均为假设，需实测验证）
> 开源路线（Odoo 双版本三仓分层，ADR-12）：core-sdk/（Apache-2.0：边缘 SDK、wire 协议——OEM 固件静态链接必须零 copyleft）；ce/（LGPL-3 社区版：设备 MCP 接入与 Legacy Bridge、MCP 聚合、基础 HITL 单级审批、单机部署形态）；ee/（源码可见商业许可企业版：管理控制台、多租户 RBAC/SSO、审计中心、多级审批、集群 HA、LLM 网关计量、配额、私有化包、等保模块）

## 0. 结论先行

**总体判定**：原方案完成了"设备反向 WSS 隧道 + JSON-RPC 工具调用 + HITL 拦截"的最小技术闭环，方向正确、代码结构清晰，但当前状态是**技术验证原型（PoC）而非可产品化系统**。核心结论：

1. **安全上不可上线**：HITL 审批回调、Agent 端点、设备凭证三个信任边界全部可被绕过或重放（SEC-01/02/03 均为阻断级），高危工业指令的 HITL 熔断形同虚设。
2. **架构上缺半边**：只有数据面（设备隧道、Agent 路由、HITL 回调挤在一个进程），控制面（租户管理、设备台账、审批流配置、审计查询）完全缺失；第 3 章设计的 PostgreSQL 三张表在代码中零接入。
3. **跨节点正确性有硬伤**：Redis Pub/Sub 无重试会静默丢消息；`adc:hitl:resolve` 通道无任何订阅者导致跨节点审批永远等不到结果；设备路由 TTL 无续期导致在线设备被误判离线。
4. **产品化缺口密集**：LLM 网关、可观测、边缘 SDK、计量计费、多区域、私有化交付、标准协议接入（原生 MCP 设备/A2A）与全栈 i18n 均为"选型挂名"或缺失状态，需按本文第 6 章五阶段路线补齐。
5. **建议路径**：先做阶段 0 安全加固（阻断项两周内修复），再做控制面/数据面轻拆分，随后按 ADR 决策替换消息层（NATS JetStream）与审批状态存储（PostgreSQL），最后进入商业化与生态阶段。

## 2. 代码级安全评审

### 2.1 信任边界梳理

本系统有 5 条信任边界，全部存在未设防或弱设防问题：

1. **设备 -> 网关**（WSS 隧道）：凭证硬编码、可重放、明文传输。
2. **Agent -> 网关**（HTTP API）：仅 X-Tenant-ID 头，无任何身份校验。
3. **审批人 -> 网关**（/v1/hitl/action）：无身份校验、URL 无签名。
4. **网关实例 <-> 网关实例**（Redis Pub/Sub）：Redis 无密码、通道无 ACL。
5. **网关 -> 企微/钉钉**（webhook）：密钥暴露在进程参数、推送失败静默。

### 2.2 威胁建模结果（STRIDE）

| 威胁 | 分类 | 攻击路径 | 可能性 | 影响 | 现有缓解 | 残余风险 |
|---|---|---|---|---|---|---|
| 冒名调用高危工具 | Spoofing | 伪造 X-Tenant-ID 调 /v1/agent/mcp/tools/call | 高 | 高 | 无 | 任意租户设备可被驱动 |
| 冒名审批高危操作 | Spoofing | 持有 ticket_id 即可 approve/reject | 高 | 高 | 无 | HITL 熔断失效 |
| 设备凭证重放 | Spoofing | 固定 HMAC 值被截获后无限重放 | 高 | 高 | 无（注释声称防重放，实为固定值） | 设备身份可长期冒充 |
| 传输内容篡改 | Tampering | ws:// 明文隧道中间人修改指令 | 中 | 高 | 无 | 下发指令被篡改 |
| 审批行为不可抵赖 | Repudiation | 审批人硬编码 "DutyEngineer"，无落库 | 高 | 中 | 无 | 无法追溯谁批的 |
| 调用行为不可审计 | Repudiation | mcp_call_logs 表从未写入 | 高 | 中 | 无 | 无审计留痕 |
| 密钥泄露 | Information Disclosure | 硬编码凭证、webhook key 在进程参数 | 高 | 高 | 无 | 凭证/密钥扩散 |
| 跨租户数据泄露 | Information Disclosure | X-Tenant-ID 任意指定 + 工具聚合无隔离 | 高 | 高 | 仅 Redis key 前缀 | 租户间工具/设备互见 |
| 慢速攻击/资源耗尽 | DoS | HTTP 无超时、无 body 限制、无限流 | 中 | 高 | WS 有 512KB 限制（4.3 节 285 行） | 服务不可用 |
| 跨站 WebSocket 劫持 | Elevation of Privilege | CheckOrigin 恒 true | 中 | 中 | 设备头鉴权部分抵消 | 浏览器上下文滥用 |
| 风险判定绕过 | Elevation of Privilege | 关键字名单不命中即免审 | 中 | 高 | 无 | 高危工具绕过 HITL |

### 4.3 关键数据流

1. **设备上线流**：原生 MCP Server 设备经注册治理中心完成 OAuth 2.1 鉴权绑定 → 平台作为 MCP Client 经 Streamable HTTP 发起 initialize 握手协商能力 → tools/list 拉取（含 schema_version、risk 建议值）→ 治理中心写 Valkey 心跳、控制面异步落库/更新台账 → Agent API 聚合时按租户与配额提供工具视图；B 类遗留设备经 Legacy Bridge（WSS + SDK 桥接）兼容接入同一台账。
2. **工具调用 + HITL 流**：Agent（OIDC/API Key 认证）→ Agent API 校验租户绑定与配额 → OPA 风险决策 → 高危则创建 PG 工单并推卡片（含签名回调）→ 审批人回调（OAuth 身份 + 验签）→ Approval Service 原子更新状态机 → JetStream 事件唤醒挂起调用 → 设备接入网关经 MCP Streamable HTTP 调用设备 tools/call 下发（Legacy Bridge 设备经 WSS 隧道下发）→ 审计流异步落库。
3. **审计与计量流**：Agent API/Approval Service/控制面产生结构化审计事件 → JetStream audit 流 → 审计服务写入 PG 分区表 → 控制台查询；同时生成用量事件供计费聚合。
4. **设备 MCP 绑定流**：设备侧向注册治理中心发起注册 → 平台校验设备身份后完成 OAuth 2.1 授权码/设备授权流程，签发绑定令牌并关联租户与设备台账 → 绑定完成后平台方可作为 MCP Client 连接设备 MCP Server 拉取工具，未绑定设备拒绝接入（ADR-15）。
5. **A2A 委派流**：外部 Agent 经平台发布的 Agent Card 发起任务委派 → A2A 网关鉴权（OAuth/API Key）并校验委派权限 → 内部多 Agent 编排流水线解析任务（编排/设备选择/执行/审批，ADR-17）→ 设备协同执行结果经 A2A 协议回传委派方 → 全链路审计事件落库（ADR-16）。

## 5. 关键决策 ADR 表

| 决策点 | 备选方案 | 选择 | 核心理由 |
|---|---|---|---|
| ADR-01 服务拆分形态 | A. 保持单进程（现状）；B. 控制面/数据面轻拆分（Admin API 独立，数据面拆设备 MCP 接入与注册治理/Agent API/Approval 三服务）；C. 全面微服务 | B | 现状单进程无法为控制面单独设防与扩缩容；C 对当前团队过重。以业务能力为界二分，数据面保持少量服务可水平扩展 |
| ADR-02 跨节点消息通道 | A. 保留 Redis Pub/Sub + 自建重试/应答；B. NATS core 请求应答；C. NATS JetStream | C | 原方案第 2 章已列 nats 但未使用。Pub/Sub 无持久、无重试会静默丢消息（SEC-10/14 根因）；JetStream 提供持久、重试、消费组，一次迁移同时解决路由与审计/审批事件流三件事 |
| ADR-03 Agent 侧 MCP 传输 | A. 自定义 JSON-RPC HTTP（现状）；B. SSE；C. Streamable HTTP（MCP 2025-03 规范） | C | 标准 MCP 客户端可直接接入，生态红利大；SSE 已被新规范取代。设备面传输走向由 ADR-15 决策（原生 MCP 为主、WSS 降级 Legacy Bridge），本 ADR 仅定 Agent 面标准化 |
| ADR-04 设备凭证方案 | A. 静态 token + 固定 HMAC（现状）；B. HMAC + nonce + timestamp（服务端签发挑战）；C. mTLS 双向证书 | B 先行，C 为终态 | 原生 MCP 设备的接入鉴权绑定由 OAuth 2.1 承载（ADR-15），本 ADR 覆盖 Legacy Bridge 设备凭证与传输层：mTLS 最安全但嵌入式证书管理与设备改造成本高；B 改动小、可立即消除重放。路线：阶段 0 落地 B，阶段 3 在高端设备推行 C |
| ADR-05 HITL 审批状态存储 | A. Redis 仅存（现状）；B. Redis 主存 + PG 留痕；C. PG 主存状态机 + Redis 唤醒/缓存 | C | 审批是合规与追责核心数据，必须持久且不可抵赖（SEC-08）；C 消除重启丢失与 24h 留痕限制，Redis 退化纯唤醒通道 |
| ADR-06 审计日志落库链路 | A. 同步写 PG（阻塞调用链）；B. 异步经 JetStream 落 PG 分区表；C. 旁路日志采集（ELK） | B | A 影响调用时延；C 丢失结构化查询能力。B 兼顾性能与可靠性，JetStream 持久保证不丢 |
| ADR-07 风险判定引擎 | A. 关键字名单（现状）；B. DB risk_level 元数据 + 规则表；C. OPA 策略（casbin 备选） | C | 关键字可绕过（SEC-09）；B 灵活性不足；原方案已列 casbin/opa。OPA 承载风险判定、租户授权、配额策略，单一决策点便于审计 |
| ADR-08 边缘 SDK 语言 | A. 纯 C；B. 纯 Rust；C. C 内核 + 多语言绑定（Rust/嵌入式平台封装） | C | ESP32/RTOS 需 C 内核与最小资源占用；Linux 盒子/高配设备用 Rust 封装获内存安全。一套 wire 契约，多语言适配 |
| ADR-09 私有化部署形态 | A. 全量 K8s 交付；B. Docker Compose 单机起步 + 轻量一体二进制目标；C. 客户自建 K8s | B | 离散制造现场多为 1-2 台服务器；Compose 交付成本最低，目标收敛为单二进制内嵌可选组件，适配内网与离线安装 |
| ADR-10 长任务执行模型 | A. 同步 HTTP + 超时（现状）；B. 异步任务 + 轮询结果；C. 异步任务 + 流式进度通知 | C | 15 秒硬超时不可承载工业长流程；流式通知匹配 MCP 生态演进方向，同时兼容轮询降级 |
| ADR-11 多区域演进 | A. 单一全局集群（现状）；B. 区域 cell（区域自治 + 跨区路由层）；C. 全双活 | B（阶段 3 后） | 制造客户有数据驻留要求；cell 隔离故障域与合规域，跨区仅控制面元数据同步，避免过早分布式复杂度 |
| ADR-12 仓库与许可证分层 | A. 双仓库（开源/闭源分离）；B. monorepo core/ + enterprise/ 二分（GitLab EE 模式）；C. 全闭源 + 外围开源；D. monorepo core-sdk/ + ce/ + ee/ 三分（Odoo 双版本模式） | D | 企业功能需复用社区版内部接口（seam），同仓分层便于同步演进与原子重构；core-sdk/（Apache-2.0）承载被 OEM 静态链接进固件的 SDK 与协议，必须零 copyleft；ce/（LGPL-3）平台主体开源，弱传染仅约束对 ce 代码本身的修改回馈；ee/（源码可见商业许可）随商业授权可见可审计，保住收入锚点；CI 独立构建验证 core-sdk/ 与 ce/ 可独立编译；B 二分无法满足 SDK 固件嵌入场景，C 放弃开源生态红利，与 Open Core 路线矛盾 |
| ADR-13 Redis→Valkey 替换 | A. 锁定 Redis 7.2（BSD-3）不接受上游升级；B. 升级 Redis 7.4+ 并接受 RSALv2/SSPLv1；C. 迁移 Valkey（BSD-3，Linux 基金会托管，API 兼容） | C | Redis 7.4 起 RSALv2/SSPLv1 与开源核心对外分发冲突；Valkey 为 Redis 的社区 fork，BSD-3 且 API 兼容，客户端与运维工具链不变，替换成本低；同时满足 Open Core 部署栈全开源可审计 |
| ADR-14 企业功能 seam 装配模式 | A. Go build tag（编译期切换）；B. 接口 + 插件注册（编译期内聚 + 运行期注册）；C. 独立企业服务进程 | B | 编译期内聚使 ee/ 企业功能可复用 ce/ 核心内部接口，运行期注册避免 ee/ 代码被 ce/ 静态 import 污染，ce/ 开源仓库构建不受影响；限制：seam 接口成为公开契约，需冻结并语义化版本管理；A 产生多构建矩阵且许可混染难以审计，C 跨进程无法复用内部接口且运维成本最高 |
| ADR-15 设备接入传输 | A. 维持私有 WSS 隧道为主（现状）；B. 原生 MCP Streamable HTTP 为主 + WSS 桥接 B 类设备；C. 双栈并列 | B | 标准 MCP Server 设备可直接暴露能力、平台作为 MCP Client 主动接入，标准生态兼容最大化（GAP-14）；平台角色从"隧道网关"转为"注册治理中心"（OAuth 2.1 鉴权绑定）；原 WSS 保留为 Legacy Bridge 兼容路径，经 SDK 桥接遗留设备，B 类设备零改造平滑过渡 |
| ADR-16 A2A 集成层 | A. 自研编排协议；B. 实现 A2A 规范（Agent Card + 任务委派）；C. 仅 MCP 不引入 A2A | B | 多 Agent 协同属 A2A 范畴，自研协议造成生态孤岛（GAP-15）；借 A2A 生态免重复建设；A2A 与 MCP 分工明确：MCP 管工具调用、A2A 管 Agent 间协作委派，互补不替代 |
| ADR-17 内部多 Agent 编排架构 | A. 单 Agent 大 Prompt；B. 固定流水线多 Agent（编排/设备选择/执行/审批）；C. 全动态 Agent 编排 | B 起步，演进 C | 固定流水线各环节独立可评测、可降级、幻觉可控，匹配工业场景确定性要求；A 不可审计、不可降级；C 复杂度高且评测体系未建立，待阶段 4 生态与评测能力成熟后渐进开放 |
| ADR-18 i18n 基础设施 | A. 后端 go-i18n + 前端 vue-i18n + 文档双语；B. 仅前端翻译；C. 英文为主、中文翻译 | A | 全栈多语言才能覆盖审批卡片/HITL 通知/后端错误消息等非 UI 触点（GAP-16）；词条治理：统一术语表 + 复译回译校验防语义漂移；工具描述多语言来源策略为"设备上报英文源 + 平台覆盖层翻译"，设备侧不重复维护 |
| ADR-19 统一 API 网关 | A. nginx 纯反代；B. Go 网关服务（路由/鉴权透传/限流/契约校验，nginx 仅静态与 TLS）；C. Python 网关 | B | 前端唯一入口，后端 Go/Python 语言与路由变更对前端无感（方案 A 双语言前提）；鉴权透传与契约校验集中一处，与数据面同栈可复用 pkg/ratelimit 与错误码体系；Python 网关性能与生态收益均无（design/70 评估）；nginx 仅静态与 TLS 终结 |
| ADR-20 Python Agent 面落地 | A. 全 Python（数据面亦 Python）；B. 混合：Go 数据面 + Python Agent 面（统一网关路由，方案 A）；C. 全 Go | B（方案 A，经 design/70 批准） | 数据面保 Go 低内存/高连接/单二进制优势；Agent 面（LLM 网关/编排/A2A/评测）用官方 MCP/A2A Python SDK 与 LangGraph（design/70 事实核实）；V1.0 交付最小集（评测工具链）、V1.5 完整（FR-012/022/024）；前后端经统一网关（ADR-19）无感切换 |

## 6. 产品化演进路线

在原方案三阶段（第 9 章 1559-1575 行）基础上重排为五阶段，阶段 0 与阶段 1 可并行，阶段 2 是 SaaS 上线门槛。

### 阶段 0：安全加固（约 1 个月，前置一切）

- **目标**：消除全部阻断级与严重级安全发现（SEC-01 至 SEC-14），达到可对外联调的安全下限。
- **范围**：Agent 认证与租户绑定（SEC-02）；HITL 回调 OAuth + 签名（SEC-01）；设备凭证 nonce 防重放（SEC-03）；全链路 TLS（SEC-05/06）；CheckOrigin 白名单（SEC-04）；风险判定改 DB 元数据过渡方案（SEC-09，正式版随 ADR-07 迁 OPA）；HITL 唤醒通道修复（SEC-10）；限流中间件（SEC-12）；审计最小落库（SEC-07）；密钥注入改造（SEC-13）。
- **开源筹备起点**：仓库按 core-sdk/ + ce/ + ee/ 三分层并冻结 seam 接口（ADR-12/14）；SEC-06 的通道加固直接落地在 Valkey 部署栈上（ADR-13），不对将被替换组件重复投资；mock 密钥等敏感信息清理启动（SEC-25，见 7.3 节）。
- **风险**：鉴权改造影响 mock 设备与早期联调客户端，需同步发布客户端凭证签发接口；工期紧张时 OPA 可后移。
- **回退**：改造以配置开关灰度（新鉴权模式默认关闭），异常回退旧模式 1 小时内完成。

### 阶段 1：MVP 控制面补全（约 2 个月，对齐原阶段一）

- **目标**：交付可演示的最小闭环：设备登记、Agent 管理、基础台账与审计查询。
- **范围**：控制面 Admin API + 简单 Web 控制台（租户/设备/Agent 凭证管理，GAP-01）；PG 三表接入读写（GAP-11）；设备心跳与 last_heartbeat（SEC-17）；设备重连踢旧连接（SEC-15）；路由 TTL 续期（SEC-14）；协议版本协商字段（GAP-06）；文档站双语起步（英文文档，ADR-18 里程碑 1）；结构化日志与基础 Prometheus 指标（GAP-07 起步）。
- **风险**：控制面与数据面若仍同进程部署，控制面改造可能波动机密数据流——按 ADR-01 直接拆分部署（共用代码库、独立进程）。
- **回退**：控制面可独立停机回滚，不影响已连接设备。
- **开源发布里程碑**：阶段 1 结束前开源仓库（core-sdk/ 与 ce/）公开，公开门槛：License 合规清零（7.1 节依赖兼容审计表逐项通过）；SECURITY.md 与漏洞上报流程；DCO 与贡献指南；双语文档站（架构、wire 协议、快速开始）；core-sdk/ 与 ce/ 经 CI 独立构建验证（ADR-12）。

### 阶段 2：生产就绪（约 3 个月，对齐原阶段二）

- **目标**：达到 99.9% SLA 的工程能力与审计合规底线，具备 SaaS 试运行条件。
- **范围**：NATS JetStream 替换 Redis Pub/Sub（ADR-02）；HITL 状态机迁 PG（ADR-05）；审计异步落库链路（ADR-06，SEC-07 完整版）；OPA 策略中心（ADR-07）；Agent 面标准 MCP streamable HTTP（ADR-03）；原生 MCP 设备接入：设备 MCP 注册治理中心 + OAuth 2.1 鉴权绑定（ADR-15，GAP-14），原 WSS 降级为 Legacy Bridge 兼容路径；双语 UI（前端 vue-i18n 接入，ADR-18 里程碑 2）；长任务异步模型（ADR-10，SEC-16）；通知推送重试与降级（SEC-18）；压测与容量规划（1 万在线设备基线）；Langfuse 追踪与告警体系（GAP-07）。
- **风险**：消息层与审批存储双迁移叠加，需分两次发布（先消息层、后审批存储）；压测基线若无法达到需扩容数据面并优化设备接入会话模型。
- **回退**：JetStream 与 Redis Pub/Sub 双写过渡一版，异常切回 Redis 通道；PG 迁移采用双写比对后切流。

### 阶段 3：商业化（约 3 个月）

- **目标**：SaaS 收费能力 + 私有化交付能力 + 多区域扩展。
- **范围**：计量计费（用量采集、配额、账单，GAP-08）；私有化轻量部署形态与离线安装包（ADR-09，GAP-10；单机形态属 ce/ 社区版，企业交付包含集群 HA 与等保模块）；多区域 cell 路由（ADR-11）；设备 mTLS 推行（ADR-04 终态）；A2A 网关：Agent Card 发布与外部 Agent 任务委派（ADR-16，GAP-15），内部多 Agent 编排流水线起步（ADR-17）；多语言支持（后端消息 i18n 全量 + 审批卡片多语言，ADR-18 里程碑 3）；管理操作审计与合规基线（等保/ISO 27001 差距整改）；SSO/OIDC 与 MFA。
- **风险**：计费模型调整会影响已签约客户，需合同层预留灰度条款；私有化包与 SaaS 企业版共用 ee/ 代码、经 seam 接口装配（ADR-14），避免版本分叉与特性开关失控。
- **回退**：私有化首批只交付单机 Compose 形态；计费按用量后结算模式灰度（账单可改，采集先上）。

### 阶段 4：生态（约 3-6 个月，对齐原阶段三）

- **目标**：开放设备与 Agent 生态，形成平台网络效应。
- **范围**：边缘 MCP SDK C 内核 + Rust 绑定（ADR-08，GAP-04）；边缘自治与断网降级、本地队列缓存与重放（GAP-05）；工具 schema 版本管理与兼容矩阵（SEC-22）；LLM 网关与 Langfuse 全量集成与 Token 治理（GAP-03）；开发者文档（双语）与认证测试套件；原生 MCP 设备厂商招募计划：认证测试套件覆盖 MCP Server 设备即插即用、设备生态目录（ADR-15 生态兑现）；行业方案包（离散制造首发）；开源生态与社区运营：issue/PR 响应 SLA（首响 24 小时、合入 5 个工作日）、Committer 晋升与治理、Open Core 章程公开（ce/ 与 ee/ 功能切分原则，ADR-12）。
- **风险**：SDK 契约一旦发布即为长期承诺，wire 协议需冻结并版本化；边缘自治涉及设备侧改造，需与首批硬件伙伴联合验证；社区贡献进入企业版必须 DCO 签署与来源审查通过，权属不明代码不得合并。
- **回退**：SDK 以 preview 版本发布，承诺 6 个月兼容窗口；断网自治先做本地缓存（只缓存不自动执行），成熟后再开自动重放。

## 7. 开源工程与许可证合规（Open Core 配套）

Open Core 路线下开源仓库对外分发，许可证合规是发布门槛而非内部事项。本节定义依赖兼容审计基线、CI 合规门禁与敏感信息清理清单；仓库三分层（core-sdk/ + ce/ + ee/）与 seam 装配见 ADR-12/14，部署栈以 Valkey 替换 Redis 见 ADR-13。

### 7.1 依赖许可证兼容审计表

| 依赖 | 许可证 | 分发形态 | 兼容性结论 |
|---|---|---|---|
| gorilla/websocket | BSD-3 | ce/ Go 二进制静态链接（Legacy Bridge 设备隧道） | 兼容，保留版权声明 |
| nats-io（NATS Server/Go 客户端） | Apache-2.0 | ce/ 部署组件与客户端依赖 | 兼容，同许可证无冲突 |
| Valkey（Redis API 兼容 fork） | BSD-3 | ce/ 部署栈（心跳/限流/锁） | 兼容，Linux 基金会托管，消除 RSALv2/SSPLv1 冲突（ADR-13） |
| litellm | MIT | LLM 网关底座（ee/ 计量） | 兼容 |
| one-api | MIT | LLM 网关底座 | 兼容 |
| langfuse | MIT | 可观测底座 | 兼容 |
| casbin | Apache-2.0 | 授权策略引擎备选 | 兼容 |
| OPA | Apache-2.0 | 风险判定/授权/配额决策点 | 兼容 |
| PostgreSQL | PostgreSQL License | ce/ 部署栈（状态与审计主存） | 兼容 |
| go-redis | MIT | Go 客户端（对接 Valkey） | 兼容 |

结论：全部依赖为宽松许可证（MIT/BSD-3/Apache-2.0/PostgreSQL License），与 core-sdk/（Apache-2.0）和 ce/（LGPL-3）双向兼容：宽松依赖并入 LGPL-3 社区版无冲突，LGPL-3 弱传染仅约束对 ce/ 代码本身的修改回馈、不向依赖项反向传导，ee/ 源码可见商业许可不受依赖影响；不引入 GPL/AGPL 组件；部署栈全开源可审计。

### 7.2 CI 合规门禁（与 SEC 扫描并列）

- 合并与发布流水线中，许可证扫描（licensecheck/ScanCode）与 SBOM 生成（SPDX/CycloneDX）与 govulncheck 并列执行，任一失败阻断合并与发版
- 新依赖必须通过许可证审查（宽松许可证放行；copyleft 默认阻断或需隔离决策），审查结论记入许可证决策台账
- SBOM 与发布标签一一对应，随开源发布物与私有化交付包提供，满足客户软件成分清单要求
- 每季度全仓重扫许可证台账，检测上游改协议等许可证漂移

### 7.3 敏感信息与密钥清理清单（发布门禁）

- 呼应 SEC-25：mock 设备明文 token 改环境变量注入并标注仅测试用途，源码零明文密钥
- 全仓接入密钥扫描（gitleaks 类）进 CI，阻断含密钥/证书/内网地址/客户数据的提交
- 公开仓库导出前核查历史提交：含企业版代码引用、内部工具链配置、客户环境信息的提交不得进入公开仓库
- core-sdk/ 与 ce/ 经 CI 独立构建验证通过后导出为公开仓库；ee/ 目录及其依赖不进入发布物（ADR-12）

## 8. 风险与对策

| 风险 | 等级 | 缓解措施 |
|---|---|---|
| 单点故障：消息层/控制面故障导致设备不可控 | 高 | 数据面与控制面解耦部署；设备面保留本节点直连快速路径，消息层故障时本节点设备仍可用 |
| 数据一致性：路由表内存/Valkey 双源漂移 | 高 | 会话归属以 Connector 本地为准，Valkey 只作索引；TTL 续期 + 断连主动清理（SEC-14/15） |
| 团队能力缺口：NATS/OPA/mTLS 均为新组件 | 中 | 阶段 2 组件引入集中培训；OPA 策略先复用社区模板；mTLS 只在高端设备试点 |
| 假设失验：1 万在线设备、99.9% SLA 均为假设 | 高 | 阶段 2 设压测关卡，容量不足则提前扩容数据面并优化会话模型 |
| 合规风险：审计与数据驻留要求 | 中 | 审计链路按 ADR-06 前置；多区域 cell 支持数据驻留（ADR-11）；阶段 3 完成等保差距整改 |
| 生态契约锁定：SDK 与协议过早发布 | 中 | 协议版本化 + preview 兼容窗口（阶段 4 回退策略） |
| 开源后被 fork 风险：社区 fork 分裂生态、稀释品牌 | 中 | 商标保留（Apache-2.0 不授予商标使用权），发布声明明确商标使用规范；ce/ 持续演进与快速响应保持上游吸引力；seam 接口语义化版本管理，fork 无法自动获得企业版能力 |
| 许可证漂移风险：上游改协议或新增 copyleft 依赖 | 中 | 许可证扫描与 SBOM 生成进 CI 门禁（7.2 节），新依赖不合规即阻断合并；每季度全仓重扫许可证台账；依赖锁定主版本并评估上游健康度 |
| 社区贡献进入企业版的法律风险（著作权归属不明） | 中 | 入站许可 DCO 强制：所有 PR 需 Signed-off-by；进入企业版的贡献先做来源审查；对长期贡献者补充 CLA 确认雇主授权 |

## 9. 结论

1. 原方案的"设备反向 WSS + 类 MCP 工具调用 + HITL 拦截"闭环验证了核心价值假设，可继续投入，但**当前代码不可直接对外上线**：3 项阻断级安全发现使 HITL 熔断与租户隔离形同虚设。
2. 修复顺序建议：阶段 0 安全加固（阻断项 2 周内）→ 阶段 1 控制面补全 → 阶段 2 消息层与审批存储迁移 → 阶段 3 商业化 → 阶段 4 生态；所有迁移遵循"可独立上线、可回退"原则。
3. 产品化成败的关键不是单一接入通道（WSS 已验证，原生 MCP 主线见 ADR-15），而是**控制面、审计合规、计量计费、私有化交付**四个缺口与 MCP/A2A/i18n 标准化能力能否在阶段 1-4 按期补齐；1 万设备与 99.9% SLA 假设必须在阶段 2 压测中兑现或重估。
4. 验收标准：上线前阻断级与严重级安全发现清零（SEC-01 至 SEC-14）；审计与审批链路可经控制面查询并不可抵赖；压测达成容量与 SLA 假设；私有化单机部署可离线交付。
