# 06-开源战略与企业版授权方案

## 一、结论摘要

**一句话许可架构**：ADC 采用 Odoo 式双版本开源模型——社区版 CE（`ce/` 平台核心以 **LGPL-3.0** 开源，与 Odoo CE 同款；`core-sdk/` 的 SDK 与 wire 协议保持 **Apache-2.0**）+ 企业版 EE（`ee/` 附加 addons 叠加于 CE 之上，**源码对订阅客户可见、可审计、可二次开发，按商业许可授权使用、禁止再分发**）；存储栈以 Valkey 替换 Redis（结论不变，详见第五章）。

**三条关键决策**：

1. **CE 平台代码采用 LGPL-3.0（与 Odoo CE 同款），core-sdk 保持 Apache-2.0**：LGPL-3.0 阻止平台核心被闭源 fork（修改必须以 LGPL-3.0 发布），同时允许集成商与客户链接、自用而不受传染；SDK 会被 OEM 静态链接进设备固件分发，copyleft 一律禁止，Apache-2.0 维持不变。
2. **EE 采用 Odoo Enterprise License 模式，且 EE 不是独立产品**：EE = CE + `ee/` 附加 addons 模块；订阅制授权、源码随订阅交付（可见、可审计、可修改自用）、禁止再分发——"企业版也是开源的"落为"源码可得 + 可审计 + 可二开"，而非 OSI 开源许可。
3. **CE 与 EE 的边界按"能力性质"切分而非"功能大小"切分**：连接、协议、基础能力进 CE 开源形成生态护城河；治理、合规、规模化能力进 EE 以许可约束形成收入来源；边界经 seam 接口固化，CI 许可门禁守护。

## 二、战略背景：为什么选双版本开源，且企业版也开源（源码可得）

ADC 的客户是工业离散制造企业与设备商/集成商，这一客群对开源策略提出了四点硬性约束：

- **工业客户信任**：工业客户（尤其信创目录、军工、核电）采购要求代码可审计、可自部署、可断网运行，且法务会审查许可证清单。开源核心 + 企业版源码可见 + 可交付 SBOM 是过审最快的路径。
- **集成商生态**：ADC 的增长依赖集成商把 SDK 嵌入设备固件与边缘盒子。宽松许可（Apache-2.0）是他们愿意嵌入的前提；任何 copyleft 条款都会让集成商的法务一票否决。
- **出海门票**：海外工业软件采购清单普遍对开源组件友好，Apache-2.0 是国际通用语言；专有闭源产品出海需面对更重的信任与合规成本。
- **开发者心智**：MCP 生态本身是开发者驱动的社区，开源核心才能进入 MCP 生态的聚合入口与教程链路，获取自然流量与早期反馈。

四条路线的对比与取舍：

| 路线 | 描述 | 放弃理由 |
|------|------|----------|
| 全闭源 | 全部代码专有，仅提供商业授权 | 工业客户审计难通过、集成商无嵌入动力、获客依赖纯销售驱动，与 ADC 的 SDK 生态打法冲突 |
| 全开源 | 含企业功能在内的全部代码开源 | 收入模型塌陷：HITL 高级化、计量、审计是无差异化收入的命门，全开源后无商业回报支撑研发 |
| 双许可（同一代码 AGPL + 商业授权） | 开源版强制 AGPL，付费换闭源授权 | AGPL 网络条款在中国工业客户与集成商中接受度极低，私有化部署是否触发义务存在争议，销售摩擦大；且 AGPL 会吓退 OEM 固件嵌入场景 |
| **双版本开源（采纳）** | CE 平台核心 LGPL-3.0 开源 + SDK/协议 Apache-2.0，EE 以 CE 叠加附加 addons、源码对订阅客户可见（商业许可、禁止再分发） | 功能分层匹配"连接开源、治理许可"的价值分布；LGPL-3.0 防闭源 fork，EE 源码可见消除审计摩擦，许可约束保住收入 |

**为什么企业版也开源（源码可得，而非闭源）**：

三点收益：

1. **工业客户的审计、信创与等保刚需**：等保评测、信创目录申报与供应链安全审计要求"被测系统代码可检视"。闭源企业版过审只能靠保密协议与黑盒承诺，解释成本高、周期长；EE 源码随订阅交付后，客户法务与安全团队可自行审查代码路径、数据流向与加密实现，过审速度与成交率显著提升。
2. **渠道商与方案商可自主二开**：工业项目高度定制化，闭源企业版意味着所有定制必须回流到 ADC 研发，渠道商只能卖标准品；EE 源码可见后，渠道商可在授权范围内自行做本地化与行业化改造（对接 MES/ERP/SCADA、定制审批流），ADC 从"定制工厂"变成"平台 + 规则"，渠道生态才有规模复制可能（衔接 doc/04 渠道政策）。
3. **信任与生态收益**：源码可得消除厂商锁定恐惧（厂商断供时客户仍可自维），EE 模块边界与 seam 接口可见使二次开发人才池得以形成；与"闭源企业版"相比，同样是付费，客户更愿意为"可审计的付费"买单，渠道更愿意代理"可自维的产品"。

代价（与收益并列写清）：

1. **再分发禁止与合规成本**：源码可得不等于 OSI 开源——EE 代码版权归 ADC，客户仅获订阅期内的查看与修改自用权，不得转售、出租、公开发布 EE 代码或其修改版。为此需建立私有源码交付渠道（私有仓库权限、版本水印），并在每份合同中明确许可边界与违约罚则；法务与工程成本高于纯闭源（纯闭源无需管理"源码交付渠道"）。
2. **许可流失风险敞口**：源码一旦交付即脱离物理控制，防扩散只能靠许可约束与罚则而非技术手段（见第十章风险台账）。EE 的收入支柱必须定位为订阅与服务（持续更新、审计报表、等保模块、支持 SLA），而非代码保密性——这一前提须在组织内达成共识。

## 三、许可证决策矩阵

### 3.1 决策树：代码资产 × 分发形态

```text
代码资产
├── 边缘 MCP SDK（C/Rust，将被 OEM 嵌入固件分发）
│   └── Apache-2.0（强制：静态链接进固件，copyleft 一律禁止）
├── wire 协议定义（JSON-RPC 2.0 + MCP 扩展）
│   └── Apache-2.0（协议规范，鼓励生态自由实现）
├── CE 平台核心（WSS 隧道、工具聚合、基础 HITL、单机部署）
│   └── LGPL-3.0（与 Odoo CE 同款：阻止平台核心被闭源 fork，允许链接与自用）
├── EE 附加功能模块（控制台、RBAC/SSO、审计、计量、集群、等保、OEM）
│   └── 企业版许可（Odoo Enterprise License 模式：订阅授权、源码随订阅可见、禁止再分发，经 seam 接口装配）
└── 文档与示例
    └── Apache-2.0（代码示例）/ CC-BY-4.0（教程文档，可选）
```

决策树的用法：拿到一段新代码或一个新依赖时，先问"它随什么分发出去"，再问"谁嵌入它"。凡是要进入设备固件、随硬件出厂分发的代码，一律要求宽松许可（Apache-2.0/MIT/BSD）或自有版权，copyleft 零容忍；随私有化安装包交付的平台代码走 LGPL-3.0（义务 = 随交付提供源码与许可文本 + 提供重新链接机制，均可满足，见 3.3）；凡是只在我们自己的服务器上运行、不向客户交付二进制的基础设施组件，许可风险大幅下降，但仍要防范非 OSI 许可带来的采购与信创审查风险（见第五章 Redis 案例）。许可判断的触发点是"分发"，不是"使用"——这是全篇合规逻辑的地基。

### 3.2 为什么 SDK 必须 Apache-2.0

OEM 设备商的交付形态是把 SDK 静态链接进设备固件、随硬件出厂分发。若 SDK 采用 GPL 家族许可证，固件即构成衍生作品，整机需开放对应源代码——设备商的核心竞争力（工艺算法、控制逻辑）将被迫公开，任何理性 OEM 都会直接弃用 ADC。LGPL 通过动态链接隔离可部分规避，但嵌入式环境（ESP32、MCU、ROM 受限）普遍只能静态链接，LGPL 同样触发源码开放义务。Apache-2.0 无传染性、附专利授权条款（防范贡献者专利伏击）、与 BSD/MIT/ISC 系依赖完全兼容，是 OEM 嵌入场景唯一稳妥的选择。

### 3.3 为什么 CE 平台代码用 LGPL-3.0（而非 Apache-2.0）

五点论证：

1. **LGPL-3.0 阻止平台核心被闭源 fork，Apache-2.0 做不到**：Apache-2.0 允许任何下游（含公有云大厂与竞品）把 CE 平台核心 fork 后闭源、闭门改进不回馈，ADC 将失去平台演进的主导权。LGPL-3.0 是 copyleft 的最小剂量：对 LGPL 库本身的修改必须以 LGPL-3.0 发布，闭源 fork 平台核心即违约、可追责；而"仅仅链接或组合使用"不受传染。
2. **允许链接与自用，保留集成自由度**：LGPL-3.0 的核心义务落在"对库本身的修改"上，而非"使用它的程序"。客户与集成商可将自有闭源代码（工艺算法、控制逻辑、MES 对接）以动态链接或进程组合方式与 CE 集成，自有部分不触发开源义务——这是 LGPL 与 GPL/AGPL 的本质区别，也是工业生态接受它的前提。
3. **服务端分发形态的合规义务可满足**：ADC 以 Go 编译的 CE 二进制随私有化安装包交付构成"分发"，LGPL-3.0 义务 = 随交付提供 CE 对应源码与许可文本（源码本就在开源仓，直接满足）+ 提供重新链接机制（发布对象文件或明确构建说明，允许客户用修改后的 CE 重新链接）。ADC 作为版权人直接履行，无技术障碍；客户在私有内网运行、修改且不再分发时不产生任何额外义务。
4. **与 Odoo CE 对齐的生态心智**：Odoo 社区版自 9.0（2015 年）起采用 LGPL-3.0，已证明该模式可支撑全球最大的开源 ERP 生态。ADC 采用同款许可，可直接复用其法务认知、审计话术与渠道契约模板，降低整个生态的解释成本。
5. **工程红线**：`ce/` 内严禁引入 GPL-2-only、GPL-3、AGPL 依赖（组合后整体升格为 GPL 家族，将失去 LGPL 链接豁免与"CE 定位"）；LGPL-3.0 允许单向升格为 GPL-3.0 的条款 ADC 不采用、亦不向社区宣示。

### 3.4 为什么 CE 不用 AGPL

CE 在 LGPL-3.0 与 AGPL 之间选择了前者。三点理由：

1. **中国工业集成商与 OEM 对 AGPL 普遍抵触**：AGPL 的网络服务条款（第 13 条）被许多企业法务直接解读为"只要提供服务就得开放全部源码"，无论条款实际触发条件如何，法务层面一票否决是常态。双许可模式在中国工业软件市场的实际案例中大多沦为"有开源之名、无生态之实"。
2. **私有化部署场景存在争议**：AGPL 义务触发点是"修改后通过网络对外提供交互服务"。纯客户内网自用部署是否构成触发存在解释分歧；一旦客户后续将平台开放给上下游供应链访问，义务边界更模糊。**争议本身即是销售摩擦**——工业私有化大单谈判中，法务不会接受一个需要论证"到底触不触发"的许可证。
3. **许可证兼容性事实**：GPL 家族与 Apache-2.0 的关系必须说清——Apache-2.0/MIT 代码可单向并入 GPLv3/AGPLv3，但反向合并（把 GPL 代码并入 Apache-2.0 作品）会使整体被迫以 GPL 分发；GPLv2-only 与 Apache-2.0 因专利终止条款互不兼容。CE 若选 AGPL，虽能吸收 Apache-2.0/MIT 生态代码，却会把集成商的自研扩展逼到许可死角（任何衍生扩展都须以 AGPL 发布）；LGPL-3.0 保留链接豁免，集成商自有代码不受传染。

### 3.5 EE 为什么用商业许可而非 OSI 开源：若完全开源（AGPL）会摧毁授权收入

EE 的能力（计量、审计、多级审批、集群、等保、OEM）是差异化收入命门，其稀缺性必须由许可制造而非代码保密制造。采用 Odoo Enterprise License v1.0 模式的商业许可：订阅期内授权使用、源码随订阅交付、允许客户修改自用、禁止再分发、授权随订阅终止而失效（条款骨架见第九章）。

备选分析——EE 若完全 OSI 开源（如 AGPL）会摧毁授权收入：

1. **再分发合法化使订阅稀缺性归零**：AGPL 允许任何人合法再分发 EE 全部功能，客户无需向 ADC 付费即可获得计量、审计、等保全部能力，授权收入模型直接归零。
2. **AGPL 防不住私有化白嫖**：AGPL 网络条款对纯内网私有化部署不触发（与 3.4 同理），工业客户恰以私有化交付为主，等于免费获得企业能力。
3. **双许可（AGPL + 商业授权）救不回谈判地位**：一旦 EE 以 AGPL 发布，客户法务会坚持按 AGPL 免费使用，商业授权谈判地位崩塌（中国市场教训见 3.4 第 1 点）。
4. **结论**：EE 保持"源码可见 + 商业许可"是授权收入的底线。可考虑的时间维度政策是"EE 模块在 N 年后下放 CE"（业界已有企业模块随时间下放社区版的实践），但任何下放须经商业模型评审，本文档不承诺时间表。

### 3.6 什么条件下可升级 AGPL

保留"升级通道"作为白嫖防御的后手，针对 CE 平台代码，触发条件（满足其一即可启动评估，全部满足则执行）：

1. 监测到公有云厂商或大型平台将 CE 包装成托管服务对外售卖，且不回馈上游（连续两个季度无任何 PR、无署名、无商业协议）；
2. 该行为已造成可量化的收入侵蚀（如：目标客户以云厂商托管版替代 ADC 企业版，累计损失超过年收入的 15%）；
3. 评估确认切换的收益大于集成商生态流失成本。

执行方式：**仅对后续新版本**将 CE 许可证由 LGPL-3.0 切换为 AGPLv3（或 AGPL + 商业授权双许可），历史版本仍按 LGPL-3.0 继续分发、不可追溯变更；切换前 90 天在社区公告并征求意见。此条款写入本文档的目的，是向生态传达"白嫖有代价"的预期管理，而非默认选项。

**EE 模块切分说明**：原"闭源企业模块清单"全部保留为 EE 模块（`ee/` 附加 addons），但性质从"代码保密"改为"源码可见、许可受限"——EE 模块源码对订阅客户开放可见、可审计、可二次开发，许可禁止再分发。对外表述统一为"企业版源码对订阅客户开放可见"，不使用"企业版开源"字样，避免与 OSI 开源定义冲突。

**分层逻辑一句话**：连接、协议、基础能力开源——这些是生态语言，开放产生网络效应且不损失收入；治理、合规、规模化能力进 EE——这些是企业客户付费的理由，源码可见消除审计摩擦、许可约束形成能力断层（社区版单机 5 台、单级审批、无审计，企业版集群千台、多级审批、全量审计）。

## 五、依赖许可合规审计

审计方法：先建台账（组件、版本、许可证、用途、分发形态），再按"分发形态"判风险——**服务端部署不构成分发、不触发 GPL 家族义务；SDK/固件内嵌、随产品交付二进制才构成分发**；最后给出兼容结论。

| 组件 | 许可证 | 分发形态 | 与 ADC 许可证基线兼容性（core-sdk Apache-2.0 / ce LGPL-3.0） | 风险等级 | 结论 |
|------|--------|----------|--------------------------|----------|------|
| gorilla/websocket | BSD-3-Clause | 静态链接进 Go 二进制，随分发交付 | 兼容（BSD 系与 Apache-2.0 双向兼容） | 低 | 允许，保留版权声明 |
| google/uuid | BSD-3-Clause | 同上 | 兼容 | 低 | 允许 |
| nats-io/nats-server | Apache-2.0 | 服务端独立部署组件 | 兼容（同族） | 低 | 允许 |
| **Redis（≥7.4）** | **RSALv2 / SSPLv1 双许可** | 服务端独立部署组件 | 不触发 SSPL 源码义务，但双许可均**非 OSI 认证**；RSALv2 限制"提供数据库/缓存等管理服务"的商业用途，SSPLv1 要求开放服务管理软件的全部源码，已致 MongoDB 案例后云厂商与信创采购广泛抵制 | **高** | **替换为 Valkey（BSD-3-Clause，Linux 基金会托管，Redis 7.2.4 fork，协议兼容）**；部署栈、文档、CI 统一改用 Valkey |
| go-redis v9 | BSD-2-Clause | 静态链接进 Go 二进制 | 兼容；go-redis 支持 Valkey 协议，客户端层无需改动 | 低 | 允许，随 Valkey 迁移 |
| litellm | MIT | 服务端独立组件（Python 服务，进程隔离） | 兼容 | 低 | 允许；注意其 Python 依赖树需用 pip-audit/SPDX 单独建台账 |
| one-api | MIT | 服务端独立组件 | 兼容 | 低 | 允许（与 litellm 二选一或分场景，同为服务端隔离部署） |
| langfuse | MIT（核心） | 服务端独立组件 | 兼容 | 低 | 允许；企业版若深度定制需复核其云版本条款 |
| casbin | Apache-2.0 | 静态链接进 Go 二进制 | 兼容（同族） | 低 | 允许 |
| open-policy-agent (opa) | Apache-2.0 | 静态链接（库模式）或独立服务 | 兼容（同族） | 低 | 允许 |
| PostgreSQL | PostgreSQL License（BSD 风格） | 服务端独立部署组件 | 兼容 | 低 | 允许 |

**兼容性规则备忘（必须记准）**：Apache-2.0 与 MIT、BSD-2/3-Clause、ISC、PostgreSQL License 均兼容；与 GPLv2-only 因专利终止条款互不兼容；Apache-2.0 代码可单向再许可为 GPLv3/AGPLv3，反向合并会迫使整体以 GPL 家族分发——故 `core-sdk/`（Apache-2.0）严禁引入任何 GPL/LGPL/AGPL 依赖（含 Go 依赖树，需全树扫描而非仅直接依赖）。`ce/`（LGPL-3.0）可吸收 Apache-2.0/MIT/BSD 系与 LGPL-3.0（含 LGPL-2.1-or-later）依赖，但严禁 GPL-2-only、GPL-3、AGPL（组合后整体升格为 GPL 家族，失去 LGPL 链接豁免）。

**Redis 问题的完整说明**：Redis 7.4 起采用 RSALv2/SSPLv1 双许可，两者均未获 OSI 认证。ADC 将 Redis 作为服务端独立组件部署，法律上不构成分发、不触发 SSPL 义务；但实际风险在采购与合规端——信创客户与央企采购风控对 SSPL 组件普遍一刀切，Linux 主流发行版已降级或移除 Redis 包。Valkey 为 Linux 基金会托管的 Redis 7.2.4 社区 fork，BSD-3-Clause，API 与协议完全兼容，go-redis 客户端可无缝切换。**结论：全栈替换，且企业版交付物与文档中不再出现 Redis 字样，避免审计解释成本。**

**合规义务清单**：随开源仓分发 LICENSE 全文与 NOTICE（列明 gorilla/websocket、google/uuid 等 BSD 组件版权声明）；`ce/` 的私有化交付附 LGPL-3.0 全文、CE 对应源码与重新链接机制说明；每次发布随 tag 生成 SPDX/CycloneDX 格式 SBOM；私有化交付包中附完整第三方组件清单与许可文本。

**审计节奏**：本台账是动态资产而非一次性文档。新增依赖须先过许可证白名单再合入（CI 强制）；每月由专人复核全量依赖树的许可证变更与新增传递依赖；每季度输出一次合规报告（组件清册、风险项、整改状态）供管理评审；私有化大单交付前对交付包做专项复核。

**EE 与 CE 关系**：EE = CE + `ee/` 附加 addons（Odoo 式模块叠加），非独立产品；`ee/` 源码对订阅客户经私有渠道（GitHub 私有仓库成员制或客户门户）开放可见，公开仓库不含 `ee/` 目录。各目录内分别放置 `core-sdk/LICENSE`（Apache-2.0 全文）、`ce/LICENSE`（LGPL-3.0 全文）、`ee/LICENSE`（企业版许可全文与"源码可见、禁止再分发"声明）。

### 6.2 企业功能 seam 接口设计原则

1. **依赖单向**：`core-sdk/` 定义协议与 SDK，`ce/` 定义平台接口（如 `Notifier`、`Authorizer`、`AuditSink`、`ApprovalEngine` 的接口形态），`ee/` 提供实现并通过注册机制装配；**ce 永不 import ee**，构建依赖严格单向（core-sdk ← ce ← ee），保证 CE 可独立构建、EE 经 seam 装配不侵入 CE 产物。
2. **进程边界优先**：高价值企业功能（计量、审计）以独立服务进程挂接（sidecar 或独立二进制），既隔离代码也隔离许可边界，防止企业许可代码通过链接进入 CE 开源产物。
3. **协议向后兼容**：seam 接口变更走 deprecation 周期，社区版与任一企业版小版本可互操作，不因企业版升级强制社区版升级。
4. **默认实现可替换**：ce 对每个 seam 提供最小开源实现（如基础单级审批、文件审计 sink），社区可替换实现，但高级实现仅 EE 提供。

### 6.3 CI 门禁

- **许可证扫描**：go-licenses / license-eye 全依赖树扫描，分仓白名单——`core-sdk/` 白名单 Apache-2.0/MIT/BSD-2/3-Clause/ISC（GPL 家族一律阻断）；`ce/` 白名单额外允许 LGPL-3.0（含 LGPL-2.1-or-later），但 GPL-2-only、GPL-3、AGPL、SSPL、RSAL、Commons Clause 等即阻断合并；Python 组件（litellm/one-api）用 SPDX + pip-audit 单独扫描；`ee/` 另跑企业组件许可校验与源码版本水印检查。
- **SBOM 生成**：syft 每次 release 随 tag 自动生成 SPDX/CycloneDX SBOM 并附加到 GitHub Release；**不生成 SBOM 不允许发版**。
- **安全扫描**：govulncheck 全量扫描，高危漏洞阻断；secret scan（gitleaks）阻断密钥误提交；测试覆盖率红线（`ce/` 核心路径不低于 60%）。

## 七、社区治理与运营章程

**贡献流程**：fork 仓库 → 提交时以 `Signed-off-by` 签署 DCO（声明贡献者拥有代码权利并按目标仓许可证授权——`core-sdk/` 为 Apache-2.0、`ce/` 为 LGPL-3.0，即入站许可）→ 发起 PR → CI 门禁（许可 + SBOM + 测试）→ maintainer 评审 → 合入。不强制个人 CLA；企业雇主批量贡献需附公司贡献协议确认其雇主放弃对抗性主张。

**Committer 晋升**：12 个月内累计 8 个以上合入 PR、经 2 名现有 committer 提名、投票通过后晋升；连续 12 个月无活动自动转为 emeritus。

**发布节奏**：月度 patch（安全与缺陷）、季度 minor（社区版功能）；版本号语义化；每个 release 附 changelog 与 SBOM；**Roadmap 公开**（GitHub Project 公示未来 2 个季度的社区版路线）。发布冻结期：release 前一周冻结功能合入，只允许缺陷与安全修复进入；CE 与 EE 同一周期发布，EE 发布说明注明其基于的 CE 版本号，保持版本对应关系可追溯。

**SLA 承诺**：issue 首响 24 小时（工作日）；PR 首评 5 个工作日、合入（或明确拒绝理由）不超过 10 个工作日；安全漏洞走 SECURITY.md 私密通道，72 小时内确认、30 天内修复发版；critical 级漏洞 7 天内发 patch。该 SLA 对应固定的开发者关系人力预算（见第十章）。

**文档站结构（英文为主、中文双语）**：快速开始（5 分钟跑通 mock 设备）→ 协议规范（wire 协议与 MCP 扩展）→ SDK 指南（C/Rust）→ 部署指南（单机、Valkey 配置）→ 安全策略（HITL 设计、漏洞披露）→ FAQ 与 Roadmap。

**CE/EE 功能切分处理规则**（写入 CONTRIBUTING.md）：若贡献者提交的 PR 实为 EE 保留功能（如集群调度增强、审计报表、计量），maintainer 先致谢，说明该功能属 EE 边界，建议改为 seam 接口、钩子、测试或协议改进类贡献；**企业功能一律不得经社区 PR 合入 `ce/`**；`ee/` 目录不接受任何外部 PR（其源码仅对订阅客户可见）。同时设"企业版贡献者奖励"：被采纳的 seam 接口设计贡献者进入致谢名单，重大贡献可获企业版一年授权。

**国际化章程（English-first，服务全球开发者）**：

1. **英文优先**：README、文档站、Issue、PR、CHANGELOG、Release Notes 一律以英文为主语言；代码注释与提交信息强制英文。中文为辅助双语（README 附中文版链接，重要公告双语发布）；Discussions 不按语言分版，maintainer 一律英文回复，中文提问以英文回答（可附中文解释）。
2. **时区轮值**：maintainer 团队按三个时区窗口轮值（UTC+8 / UTC+1 / UTC-8），issue 首响 SLA 按"下一个轮值窗口"而非单一工作日历计算，保证全球开发者 24 小时内有响应。
3. **多语言文档贡献流程**：文档按语言目录组织（`docs/en/` 为源语言、`docs/zh/` 等为翻译）；翻译 PR 必须基于源语言最新版本、经母语者 review 后合入；新功能合入时源语言文档先行，翻译滞后不得超过一个 minor 版本周期，滞后版本在页面顶部标注对应版本提示。

| CE 被大客户白嫖 | 大客户自建基于社区版，不买企业版 | 功能自然分层：CE 仅单机部署形态、单级审批、无审计留存、无集群 HA（LGPL-3.0 下同样不能以授权限制设备数，只能以功能断层分层）；企业版销售话术以"审计合规 + 等保 + 集群"为核心而非基础功能 |
| 贡献者 IP 风险 | 贡献者夹带雇主代码或第三方代码 | DCO 签署即入站授权声明；大额 PR 要求确认雇主权益；CI 全依赖树扫描防夹带非白名单许可代码 |
| 许可证漂移 | 依赖升级引入 GPL 或变更新许可证（如上游换 SSPL） | CI 白名单门禁每次合并扫描；月度全量复核台账；对高替换成本组件（存储、消息）维持"替代栈评估"预案（如 Valkey 案例） |
| 社区运营拖累主线研发 | issue/PR 洪峰占用研发人力 | SLA 对应固定人力预算（1 名全职开发者关系岗 + bot 自动分流重复 issue）；SLA 只承诺"首响"不承诺"解决时限"，超出能力时诚实降级并公告 |
| 云厂商托管白嫖 | 云厂商将 CE 包装成托管服务 | 预埋 AGPL 升级条款（见 3.6）作威慑；EE 商业许可使其无法复制完整体验；必要时与云厂商签 OEM/托管合作协议变现 |
| EE 源码泄漏到非订阅方 | EE 源码随订阅交付后，被客户内部人员或合作方扩散至非订阅方 | 定位为许可约束而非技术约束：非订阅方使用泄漏源码无任何授权、构成侵权，EE 收入支柱是订阅与服务而非代码保密性；对策：源码版本水印与交付版本号标记（溯源泄漏点）、合同明确保密义务与 3 倍违约金罚则、重大泄漏取证后依法追责；同时以"订阅期源码托管（escrow）+ 断供条款"降低客户"先拿源码再谈"的动机 |
| CE 被 fork 闭源 | 竞品将 CE 平台核心 fork 后闭源化，闭门改进不再回馈 | LGPL-3.0 防护已内建：对 CE 的修改必须按 LGPL-3.0 发布，闭源 fork 平台核心即违约可追责；竞品只能在自有边界外叠加独立模块，而治理/审计/计量能力仍缺 EE 模块，构成许可与功能双重断层 |
