## 1. 背景与目标

### 1.1 业务背景

传统 IoT 平台将设备视为哑终端，仅做数据单向采集与静态规则流转，设备能力无法被上层 AI Agent 直接调用；而大模型与 Agent 应用爆发后，工业客户普遍存在"让 Agent 参与设备诊断、排产、维护"的诉求，却缺少一条统一、安全、受控的"设备工具化"通道。

原始技术方案（doc/Agentic Device Cloud.md）已验证核心链路可行：反向 WSS 隧道解决内网寻址、MCP tools/list 动态聚合实现设备工具化、Redis Pub/Sub 支撑集群路由、HITL 审批熔断兜底高危操作。但该方案停留在演示级：无租户体系、无管理控制台、风险判断靠关键字硬编码（`isHighRiskOperation`）、审批策略不可配置、无审计查询与导出、无计量计费、无系统监控，无法直接交付企业客户。

本 PRD 将技术方案产品化为可售卖的企业级产品，把产品化缺口（租户、控制台、API Key、风险配置、审批策略、审计、批量纳管、SDK 分发、计量计费、监控告警）显式纳入需求，并纳入三个新方向：原生 MCP 设备鉴权绑定（主线）、A2A 协同调度与全栈 i18n 国际化。

产品采用 Odoo 双版本模式：连接、协议与基础能力（原生 MCP 设备鉴权绑定、MCP 工具聚合、单机路由、基础 HITL 单级审批、Legacy Bridge 设备桥接）进入社区版（CE，LGPL-3）开源、免费自部署，不以授权条款限制使用规模；治理、合规与规模化能力（管理控制台、多租户 RBAC/SSO、审计中心、多级审批、集群 HA、LLM 网关计量、配额、私有化包、OEM 白标）进入企业版（EE），以源码可见的商业许可交付（SaaS 与私有化），通过企业功能分层实现自然商业分层。版本体系为社区版 → 企业版 SaaS → 企业版私有化。

### 1.2 产品目标（可衡量）

- G1：V1.0 发布后 6 个月内，签约 2 家离散制造种子客户，每家接入设备不低于 100 台（假设，依据：MVP 验证节奏与销售资源）。
- G2：V1.0 免审场景端到端任务成功率不低于 99%。
- G3：高危指令（风险等级 2 及以上）HITL 拦截率 100%。
- G4：V1.5 发布前，单网关节点通过 1 万在线设备压测验证（假设，依据：CNC 车间规模估算）。
- G5：V1.5 前完成等保 2.0 三级测评，支持私有化交付。

### 1.3 非目标（1.0 明确不做）

- 不做边缘自治：设备端仅执行与上报，不做断网本地 Agent 决策，平台不承诺断网自治能力。
- 不自研大模型：统一接入第三方模型供应商（含国产模型），不自训、不微调底座模型。
- 不做通用 IoT 数据采集平台：不替代 SCADA/组态软件，聚焦"动作执行通道"而非全量数据采集。
- 不做数据湖与 BI 分析：数据存储满足审计与调用链路即可。
- 不做消费级场景：不做智能家居、个人设备市场。
- 1.0 控制台 UI 仅中文首发（产品 UI 多语言在 V1.5 经 FR-023 交付）；文档与开源社区自 V1.0 起英文优先、中英双语；数据中心 V1.0 仅大陆区域，海外区域部署随国际化里程碑（FR-023）在 V1.5 后启动。
- 社区版不承诺 SLA 与商业支持：开源社区版由用户自部署、自运维，平台方不提供可用性 SLA 承诺与商业级技术支持，相关承诺仅适用于企业版（SaaS 与私有化）服务协议。
- 开源核心不包含企业合规模块：等保 2.0 三级测评、审计留证与数据出境管控等合规能力仅在企业版提供，开源核心不承担企业合规承诺。

| 用户角色 | 核心场景 | 当前痛点 | 期望收益 |
|---------|---------|---------|---------|
| 工厂设备工程师（一线运维/保全） | 设备异常时 Agent 自动诊断并申请高危操作；工程师在企业微信/钉钉手机上审批卡片，同意或拒绝执行 | 高危操作需现场跑腿确认；夜班响应慢；操作无全程留痕 | 移动审批、远程受控执行、操作可追溯 |

| Agent 开发者（MCP 客户端 + A2A 委派方） | 凭 API Key 调用租户虚拟 MCP 端点，基于自动发现的标准工具集开发设备诊断/排产 Agent；或作为 A2A 委派方向平台委派设备协同任务 | 每类设备协议不同；缺少统一 MCP 端点；高危动作不敢交给 Agent；跨平台 Agent 无法互调设备能力 | 一套标准 MCP 接口、工具自动发现、HITL 兜底安全、经 A2A 协议跨平台委派设备任务 |

| 海外设备制造商 OEM（全球视角） | 面向海外市场交付原生 MCP 设备，经平台完成端点鉴权绑定与绑定令牌接入，控制台与工具描述以英文呈现 | 海外客户对多语言与数据驻留要求高；缺乏全球可复用的设备鉴权绑定方案 | 一套绑定协议全球复用、英文控制台与文档、借平台进入 AI 设备生态 |

- 版本：指该需求首个承诺交付的版本，详见第 6 节。

### 3.4 功能需求明细

#### FR-001 设备反向接入隧道（WSS）

- 描述：设备通过 WSS 长连接反向接入云端网关，解决工业内网无公网 IP 的寻址问题；连接建立后网关可向设备下发 JSON-RPC 2.0 请求。自 V1.5 起该能力定位为 Legacy Bridge，仅服务 B 类（无原生 MCP Server 运行时）设备桥接；A 类原生 MCP 设备走 FR-021 鉴权绑定。
- 用户故事：作为边缘设备运行时（内网无公网 IP），我希望通过 WSS 长连接反向接入云端，以便云端可主动向设备下发 MCP 指令。
- RICE 依据：R=9（所有接入设备必经）；I=3（无隧道产品不成立）；C=90%（原方案已实现并验证）；E=6 人周（重连、心跳、优雅退出产品化加固）。
- KANO：基本型。
- 验收标准：
  - Given 设备已注册且携带合法凭证，When 发起 /v1/devices/tunnel 升级请求，Then 建立 WSS 连接，并在 5 秒内完成 tools/list 同步。
  - Given 隧道运行中网络闪断，When 连接断开，Then SDK 按指数退避（1 秒起步，上限 60 秒）自动重连，重连成功后重新注册工具。
  - Given 网关连续 60 秒未收到设备 Pong，When 心跳超时，Then 判定设备离线，清理本地会话与 Redis 路由，设备状态置为 offline。
  - Given 单条消息超过 512KB，When 设备发送超限消息，Then 网关拒绝并断开该连接，记录告警日志。
- 异常场景：设备凭证变更后旧连接需被踢下线；同一设备重复连接时旧会话被替代，仅保留最新会话。
- 依赖：FR-002、NFR-004。

#### FR-002 设备鉴权（Token/HMAC/mTLS）

- 描述：设备接入必须通过 Token、HMAC 签名或 mTLS 证书三种方式之一鉴权，凭证由平台签发、可吊销。
- 用户故事：作为平台管理员，我希望设备凭证可签发、可吊销、不可伪造，以便任何非法设备无法接入平台。
- RICE 依据：R=10（全量设备）；I=3（安全是工业客户购买前提）；C=90%（技术已验证）；E=4 人周（对接 KMS 与吊销列表）。
- KANO：基本型。
- 验收标准：
  - Given 设备携带无效 Token 或 HMAC 签名，When 请求建立隧道，Then 返回 403，记录鉴权失败事件。
  - Given 设备配置 mTLS 方式，When 客户端证书不在白名单或已吊销，Then 拒绝 TLS 握手。
  - Given 管理员吊销某设备凭证，When 该设备再次连接，Then 鉴权失败且已建立的旧连接被踢下线。
- 异常场景：HMAC 需支持时间戳防重放（漂移窗口 5 分钟）；同一设备支持切换鉴权方式但需二次确认。
- 依赖：FR-010、NFR-004。

#### FR-003 设备工具动态发现与聚合

- 描述：设备上线后上报 tools/list，网关以"设备码__工具名"命名空间聚合为租户级虚拟 MCP 端点，供 Agent 统一查询；设备离线时其工具自动摘除。
- 用户故事：作为 Agent 开发者，我希望设备上线后工具自动出现在租户虚拟 MCP 端点中，以便无需人工登记即可开发 Agent。
- RICE 依据：R=9；I=3（产品核心价值"设备即工具节点"）；C=90%；E=4 人周（聚合缓存与一致性处理）。
- KANO：基本型。
- 验收标准：
  - Given 设备上线并上报 N 个工具，When 网关完成同步，Then 30 秒内 Agent 可在 tools/list 中查询到以"设备码__工具名"命名的工具。
  - Given 设备离线，When Agent 查询 tools/list，Then 该设备工具不出现。
  - Given 同名工具来自不同设备，When 聚合，Then 命名空间保证全局唯一、互不覆盖。
- 异常场景：工具 input_schema 非法 JSON 时跳过并告警，不影响其余工具注册；同一设备重复上报以最新为准。
- 依赖：FR-001、FR-006。

#### FR-004 集群化工具路由（Redis Pub/Sub）

- 描述：多网关实例通过 Redis 共享设备位置与工具缓存，跨节点经 Pub/Sub 透传 tools/call 请求与响应。
- 用户故事：作为平台运维方，我希望设备连接分散在任意网关节点时调用仍可寻址，以便平台水平扩展而不中断服务。
- RICE 依据：R=8（1.0 起必须）；I=3；C=80%（多节点故障场景未充分验证，标注假设）；E=6 人周。
- KANO：基本型。
- 验收标准：
  - Given 设备连接在节点 B，When 节点 A 收到该设备的 tools/call，Then 经 Redis Pub/Sub 转发至节点 B 执行并回传结果。
  - Given 设备未在任何节点在线，When 路由查询，Then 返回"设备离线或不存在"业务错误。
  - Given 任一网关节点宕机，When 其管理设备心跳超时，Then 其余节点 90 秒内完成状态清理。
- 异常场景：Redis 主从切换期间请求需重试一次；Pub/Sub 消息投递超时 15 秒返回超时错误。
- 依赖：FR-001、NFR-003。

#### FR-005 HITL 高危指令审批（企业微信/钉钉卡片）

- 描述：风险等级 2 及以上工具调用被拦截并生成审批工单，通过企业微信/钉钉交互卡片推送给审批人，同意后执行、拒绝或超时则拦截终止，结果回传 Agent。
- 用户故事：作为工厂设备工程师，我希望高危设备操作先经过我确认再执行，以便模型误判时不会造成实体损伤。
- RICE 依据：R=8（工业安全合规刚需）；I=3（产品安全卖点）；C=85%；E=8 人周（回调安全加固与工单持久化）。
- KANO：基本型。
- 验收标准：
  - Given 工具风险等级不低于 2，When Agent 发起调用，Then 不执行并生成审批工单（Ticket UUID），30 秒内向审批人推送卡片。
  - Given 审批人在工单有效期内点击同意，When 回调校验通过，Then 指令下发执行并向 Agent 回传执行结果。
  - Given 审批人拒绝或工单超时（默认 5 分钟），When 决策生效，Then 指令不执行，Agent 收到 BLOCKED_BY_HITL 错误。
  - Given 审批卡片回调请求，When 来源签名校验失败或工单已处理，Then 拒绝处理并记录异常事件。
- 异常场景：审批中设备离线时工单自动失效并通知 Agent；卡片推送失败需重试 3 次并记录推送渠道可用性。
- 依赖：FR-006、FR-007、NFR-004。

#### FR-006 工具风险等级配置管理（替代关键字硬编码）

- 用户故事：作为平台管理员，我希望为每个设备工具配置风险等级，以便高危判断可管理、可审计、不依赖开发改代码。
- RICE 依据：R=8；I=3（硬编码误判误拦是重大缺陷）；C=90%；E=4 人周（表结构扩展与策略引擎）。
- KANO：基本型。
- 验收标准：

- 异常场景：等级下调（如 2 降至 0）需二次确认并写入审计日志；设备离线重连后等级以平台配置为准。

- 异常场景：审批人离职/不在岗时按兜底策略转发备份审批人；策略变更对在途工单不生效、仅对新工单生效。

#### FR-018 开源工程化与发布

- 描述：按 Odoo 双版本模式建设工程体系：monorepo 按 core-sdk（Apache-2.0，边缘 SDK 与 wire 协议）、ce（LGPL-3 社区版）与 ee（企业版，源码对客户可见、商业许可）三分层，补齐 LICENSE、NOTICE、CONTRIBUTING、SECURITY.md 等社区治理文件，引入 DCO 提交机器人，CI 流水线内置许可证扫描与 SBOM 生成，按月度发布节奏产出开源制品与 EE 商业许可制品，并维护版本兼容矩阵。
- 用户故事：作为社区开发者，我希望通过标准化的工程仓库参与贡献并清楚了解 core-sdk/CE/EE 许可证边界，以便可信地使用、构建与扩展社区版。
- RICE 依据：R=8（开源路线将触达开发者与生态集成商）；I=3（工程与合规基础决定开源路线的可信度与采纳）；C=85%（工程化做法成熟、可复用业界实践）；E=8 人周（三仓分层改造、合规工具链与发布流水线建设）。
- KANO：期望型。
- 验收标准：
  - Given 开发者克隆社区版仓库，When 阅读 LICENSE 与 NOTICE，Then 明确 core-sdk 为 Apache-2.0、CE 为 LGPL-3、EE 源码仅对持证客户可见，且第三方依赖归属清晰。
  - Given 贡献者提交 PR，When 缺少 DCO 签名，Then CI 门禁拦截并提示补签。
  - Given 一次发布构建，When CI 运行完成，Then 许可证扫描零高危项且产出可下载的 SBOM 与版本化制品。
  - Given CE 与 EE 同一版本发布，When 对照版本兼容矩阵，Then 核心组件与 SDK 的兼容范围及对应版本号可查询。
- 异常场景：许可证扫描发现新增高危许可证依赖时阻断合并并通知维护者；DCO 机器人不可用时 PR 保持阻断而非静默放行。
- 依赖：FR-019、FR-020。

#### FR-019 企业功能开关与版本切分

- 描述：EE 功能通过接口 seam（插件点/扩展接口）装配到 CE 之上，以 feature flag 控制开关；CE 仓库可脱离 EE 模块独立构建、运行与发布，EE 模块（源码对持证客户可见）可插拔激活并构成完整企业版制品。
- 用户故事：作为平台研发方，我希望 CE 与 EE 在同一代码基上分层演进，以便一次维护、双制品发布且版本边界清晰可控。
- RICE 依据：R=7（影响研发与社区开发者两类角色）；I=3（切分机制决定双版本模式能否落地）；C=85%（seam 与 flag 机制为成熟工程实践）；E=6 人周（接口抽象、构建矩阵与 flag 体系改造）。
- KANO：基本型。
- 验收标准：
  - Given 仅检出 CE 代码，When 执行构建与测试，Then 全部通过且可独立运行，不包含任何 EE 代码。
  - Given 部署 EE 制品并开启企业模块，When 激活对应 feature flag，Then 管理控制台、审计中心、多级审批等企业功能可用。
  - Given 关闭某企业 feature flag，When 系统运行，Then 该功能链路降级为社区版行为且不影响核心链路。
- 异常场景：EE 模块误引用 CE 内部实现导致边界泄漏时 CI 直接报错；flag 配置漂移需在发布前通过一致性检查。
- 依赖：FR-018。

#### FR-020 开源文档站与示例工程

- 描述：提供社区版（CE）文档站（快速开始、API 文档、架构说明）与示例工程（示例 Agent 与硬件示例工程），覆盖"克隆、构建、跑通第一条设备 MCP 调用"的最小上手路径。
- 用户故事：作为社区开发者，我希望按快速开始文档在最短时间内跑通设备接入与 Agent 调用示例，以便低成本评估与二次开发。
- RICE 依据：R=7（文档与示例是开源采纳的入口）；I=2（加速采纳，非核心功能）；C=80%（示例工程需覆盖多硬件平台，存在打磨成本）；E=6 人周（文档站建设与两类示例工程）。
- KANO：期望型。
- 验收标准：
  - Given 开发者按快速开始操作，When 完成全部步骤，Then 1 小时内实现设备接入并完成一次 Agent 工具调用。
  - Given 文档站上线，When 开发者访问 API 文档，Then 可按接口与版本检索并附请求响应示例。
  - Given 硬件示例工程，When 开发者按目标平台构建烧录，Then 设备注册并上线为 MCP 工具节点。
- 异常场景：文档与当前版本不一致时需标注对应版本号并提示过期；示例工程随核心版本同步更新，旧版示例标注兼容范围。
- 依赖：FR-018、FR-019。

#### FR-021 原生 MCP 设备鉴权绑定

- 描述：面向原生带 MCP Server 运行时的设备（A 类设备），平台对设备 MCP 端点做注册与鉴权绑定：设备身份注册、OAuth 2.1 客户端凭证绑定、绑定令牌签发防中间人、生命周期管理（注册/绑定/心跳/吊销/解绑）；原 WSS 隧道自本需求起降级为 Legacy Bridge，仅供 B 类（经边缘 SDK 桥接）设备使用。
- 用户故事：作为设备制造商 OEM，我希望设备出厂自带 MCP Server 运行时并向平台注册端点完成 OAuth 2.1 鉴权绑定，以便设备能力被平台安全代理为可编排的标准工具。
- RICE 依据：R=9（所有原生 MCP 设备必经）；I=3（安全绑定是设备方向主线成立前提）；C=80%（OAuth 2.1 绑定流程与存量接入改造存在不确定性）；E=8 人周（注册/绑定/生命周期状态机与令牌体系）。
- KANO：基本型。
- 验收标准：
  - Given 设备出厂自带 MCP Server 运行时，When 厂商提交注册信息（厂商、型号、MCP 端点），Then 平台完成设备身份注册（登记公钥指纹）并经 OAuth 2.1 客户端凭证授权完成端点绑定，签发绑定令牌。
  - Given 设备已完成绑定，When 平台经绑定令牌发起 MCP 端点调用，Then 令牌校验通过且仅限已绑定端点使用，端点被替换或中间人转发时拒绝调用并告警。
  - Given 心跳超时或厂商发起吊销/解绑，When 生命周期事件生效，Then 端点立即从工具聚合摘除、令牌失效并记录审计。
- 异常场景：绑定令牌默认 24 小时有效期，轮换失败自动吊销；同一端点重复注册时旧绑定失效；OAuth 2.1 授权服务器不可用时绑定请求快速失败并告警。
- 依赖：FR-003、FR-010、NFR-004。

#### FR-022 A2A Agent Card 与任务委派

- 描述：平台发布 A2A Agent Card 向外部编排 Agent 开放设备协同能力，接收委派任务（任务类型：诊断/排产/巡检/维护处置），支持任务级权限与租户绑定，HITL 审批语义（待审批/同意/拒绝/超时）随任务状态机回传委派方。
- 用户故事：作为外部 AI 编排器开发者，我希望通过平台发布的 A2A Agent Card 发现设备协同能力并委派任务，以便编排 Agent 无需直连设备即可完成跨平台设备协同。
- RICE 依据：R=7（A2A 生态早期，触达面取决于生态成熟度）；I=3（打开设备能力对外编排通道）；C=70%（A2A 规范尚处早期、生态未规模化，标注假设）；E=10 人周（Agent Card、委派任务状态机与 HITL 语义映射）。
- KANO：兴奋型。
- 验收标准：
  - Given 平台已配置对外 Agent Card，When 外部 Agent 拉取，Then 获取能力描述、支持的任务类型与鉴权方式，Card 内容支持英文与中文双语。
  - Given 外部 Agent 持有效委派凭证，When 提交诊断任务，Then 任务绑定其所属租户与授权范围，越权工具调用返回 403。
  - Given 委派任务触发高危操作，When 进入 HITL 审批，Then 任务状态与审批语义经 A2A 协议回传委派方，审批结果驱动后续执行。
- 异常场景：委派方失联时任务按租户默认超时策略收敛并告警；Agent Card 变更需版本化并通知订阅方；恶意高频委派触发任务级限流。
- 依赖：FR-008、FR-024、NFR-004。

#### FR-023 全栈 i18n 与本地化

- 描述：全栈多语言：后端消息、前端控制台 UI、审批卡片、工具描述、错误码、Agent Card 全部国际化，英文+中文首发；建立术语表治理机制，日期/时区/计量单位按区域本地化。
- 用户故事：作为海外设备制造商 OEM，我希望控制台、审批卡片与工具描述以英文呈现且日期单位按本地习惯展示，以便海外团队与终端客户无障碍使用平台。
- RICE 依据：R=8（面向海外 OEM 与 A2A 生态）；I=2（拓展海外市场的必要能力）；C=90%（i18n 工程成熟、可复用业界实践）；E=6 人周（全栈文案抽取、语言包与本地化测试）。
- KANO：期望型。
- 验收标准：
  - Given 用户切换语言偏好为英文，When 访问控制台、审批卡片与 Agent Card，Then 界面、审批卡片、工具描述、错误码全部英文呈现，日期/时区/单位按区域格式本地化。
  - Given 新增一条术语，When 经术语表治理流程发布，Then 该术语在全栈语言包中一致生效。
  - Given 存在缺失翻译词条，When 渲染，Then 回退默认语言并记录缺失告警，不出现乱码或空文案。
- 异常场景：语言包与版本不同步时阻断发版；用户语言偏好持久化且与审批卡片推送渠道语言一致；RTL 语言不在 V1.5 范围。
- 依赖：FR-014、FR-020、FR-022。

#### FR-024 内部多 Agent 编排引擎

- 描述：平台内部多 Agent 固定流水线：编排规划→设备选择→执行→HITL 审批，由任务状态机（待规划/规划完成/执行中/待审批/已完成/失败）驱动，支持失败重试与降级（单 Agent 直调兜底），编排过程可评测（成功率/时延/审批介入率）。
- 用户故事：作为自动化/生产负责人，我希望向平台下达自然语言任务后由内部多 Agent 完成规划与设备选择并在 HITL 约束下执行，以便复杂协同任务无需人工拆分。
- RICE 依据：R=7（覆盖全部委派与协同任务场景）；I=3（从单工具调用升级为任务级编排，价值跃升）；C=75%（多 Agent 编排效果依赖模型能力，标注假设）；E=12 人周（流水线、状态机、重试降级与评测体系）。
- KANO：期望型。
- 验收标准：
  - Given 提交一个协同任务，When 编排引擎处理，Then 按规划→设备选择→执行→HITL 审批流水线推进，状态机完整落库且可查询。
  - Given 执行阶段失败，When 达到重试上限，Then 按降级策略处理（LLM 网关不可用时以固定规则模板完成只读类任务）或终止任务并回传失败原因。
  - Given 任务完成，When 查询评测指标，Then 可获取端到端成功率、时延与审批介入次数。
- 异常场景：规划阶段超时熔断并降级；设备选择结果为空时终止并回传可诊断信息；并发任务按租户限流。
- 依赖：FR-003、FR-005、FR-012、FR-021。

## 5. 数据指标与埋点

| 指标 | 定义 | 目标值 | 埋点事件 |
|------|------|--------|---------|
| 设备在线数 | 每日最大同时在线设备数（按租户统计） | 上线 3 个月后种子租户不低于 100 台（假设） | device_connected / device_disconnected |
| 设备在线率 | 在线时长 ÷ 应在线时长（工作日） | 不低于 99% | 心跳事件 heartbeat_ok / heartbeat_lost |
| Agent 调用量 | 每日 tools/call 请求次数（按租户/Key） | 商业化首月月环比增长不低于 20%（假设） | tool_call_start |
| HITL 拦截率 | 拦截次数 ÷ 高危工具调用总次数 | 100% | hitl_intercepted |
| 审批时效 | 卡片下发到审批完成的时间 | P95 不超过 5 分钟 | hitl_created / hitl_resolved |
| 审批通过率 | 同意 ÷（同意+拒绝），超时不计入 | 观测值，无目标 | hitl_resolved |
| 端到端任务成功率 | 成功调用 ÷ 总调用次数（免审场景） | 不低于 99% | tool_call_end |
| 指令下发时延 | 平台收到 tools/call 到设备回包的时间（免审） | P95 不超过 500ms | tool_call_start / tool_call_end |
| 工具发现时延 | 设备上线到其工具对 Agent 可见 | 不超过 30 秒 | device_connected / tools_synced |
| 周活跃 Agent Key | 一周内至少发起 1 次调用的 API Key 数 | 观测值，无目标 | api_key_call |

埋点规范：所有事件含 tenant_id、event_time（Asia/Shanghai）、trace_id；trace_id 贯通设备接入、工具调用、HITL 工单与审计日志；埋点失败不影响主链路（FR-016）。

发布与版本体系（Odoo 双版本）：社区版（CE，LGPL-3 开源）与企业版（EE，源码可见商业许可）同源发布，同一 tag 产出开源制品（core-sdk + CE）与 EE 商业许可制品；版本体系为社区版（开源免费自部署，功能自然分层，不以授权限制设备数）→ 企业版 SaaS → 企业版私有化。

## 7. 风险与开放问题

### 7.1 风险清单

1. MCP 协议快速演进风险：MCP 规范仍处快速迭代期，可能出现不兼容变更，网关需做协议版本协商与兼容层，SDK 需支持灰度升级；否则已出货设备存在失联风险。
2. LLM 幻觉导致误操作的残余风险：HITL 仅覆盖高危工具，低危写入与参数篡改（幻觉生成危险参数）仍可能造成损失，需在参数级做范围校验与二次确认策略研究。
3. 边缘 SDK 生态冷启动风险：OEM 集成意愿取决于订单规模预期，若无种子订单背书，SDK 投入可能空转，需与 1-2 家 OEM 签联合开发协议先行锁定。
4. 跨厂商协议适配成本高：CNC/PLC 协议碎片化（FANUC FOCAS、Siemens 840D、Modbus、OPC-UA），每类设备适配 4-8 人周，需用插件化适配器架构摊薄成本并优先高频机型。
5. 审批时效与产线节拍冲突：默认 5 分钟审批超时可能低于人工响应速度，导致高危任务频繁失败，需按行业实测调整超时与免审策略（观察指标：审批时效 P95）。
6. 工业内网弱网下 WSS 稳定性：车间 Wi-Fi/4G 抖动频繁，重连风暴可能击穿网关，需重连退避、限流与连接数上限保护。
7. 等保三级周期长影响商业化：测评通常需 3-6 个月，若等保未过将阻断大陆企业客户签约，V1.5 前需预留整改周期并提前启动安全建设。
8. 数据出境合规风险：工具描述、调用参数与响应可能经境外模型 API 流转，违反《数据安全法》要求，需提供国产模型默认路由与敏感字段过滤（NFR-005 兜底）。
9. 多租户隔离与 Redis 键冲突风险：Redis 键空间按 tenant:device 设计，若隔离逻辑缺陷将导致跨租户指令串扰，属最高安全级别缺陷，需专项测试。
10. 审批卡片回调伪造风险：回调 URL 含 ticket_id 且可被猜测，需签名校验、工单一次性消费与来源白名单，否则攻击者可放行高危指令。
11. 第三方 LLM 供应商依赖风险：供应商故障或政策变化将影响 LLM 网关可用性，需多供应商冗余与降级策略（FR-012 已纳入故障转移）。
12. 定价模式未验证风险：按设备数、调用量或混合计费尚无客户验证，定价失误将影响续约，V1.5 前需完成种子客户付费意愿测试。
13. A2A 规范早期风险：A2A 协议尚处早期演进期，规范变更可能带来协议不兼容与委派方适配成本，需做协议版本协商与兼容层，并以少量种子编排器联调验证（FR-022 C=70% 假设）。
14. 原生 MCP 设备市场未规模化风险：当前原生带 MCP Server 运行时的设备厂商有限，若生态迟迟不起量 FR-021 投入可能空转，需与 1-2 家厂商签联合开发协议锁定种子设备，并与 FR-015 SDK 生态冷启动协同推进。
15. i18n 多语言质量治理风险：多语言文案（含工具描述与审批卡片）翻译质量与术语一致性难以保证，错误文案可能误导高危操作审批，需建立术语表治理与本地化验收流程，由行业背景译员完成翻译并辅以机器检测兜底。

### 7.2 开放问题

1. 交付形态：大陆制造业普遍倾向私有化部署，SaaS 与私有化的代码与运维体系如何统一，需架构侧给出答案（ADR）。
2. 模型供应商选型：国产模型与海外模型的能力差距、成本与合规边界需实测，形成默认供应商清单。
3. 审批人组织同步：企业微信/钉钉通讯录与平台角色的同步方式（手动/API 对接）待与种子客户确认。
4. mTLS PKI 体系：设备证书的签发、轮换与 CRL 吊销由平台自建还是对接客户 PKI，待定。
5. 计费单位：设备数与调用量的混合计费公式、免费额度与梯度价格待商业化前验证。
6. HITL 回调网络可达性：内网工厂审批人点击卡片后需访问公网回调地址，私有化部署下回调链路需重新设计。
7. 设备固件升级通道：是否复用 MCP 隧道做 OTA，还是独立通道，涉及安全面扩大，待定。
8. 与客户既有系统集成：与 MES/ERP 的对接范围（排产指令来源）在 1.0 是否纳入，待与种子客户确认后决定。
